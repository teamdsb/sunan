# M9 Wave 2 提示词：全通讯录与用户授权后端

> 状态：本 Wave 后端已实施并完成有条件验收；真实企业微信全目录、生产存量对账和现场设备验证仍属于后续 W5。后续修改须继续遵守本提示词的固定约束。

## 目标与前置

实现全企业成员同步及用户授权管理，保证人工设置在重新认证、刷新和同步后保持。

W1 契约与迁移方案已完成；范围不清的权限差异先按已冻结矩阵处理。

## 本 Wave 工作

1. 执行 M9-W2A：增量迁移来源/覆盖/账号状态/授权版本/审计及同步批次，保留用户UUID与外键，不迁移成多租户系统。
2. 执行 M9-W2B：主应用通讯录读取与手动同步，覆盖未登录成员、多部门、分页、去重、部分失败及覆盖范围；缺失名单不等于离职。
3. 执行 M9-W2C：统一有效授权服务，接入OAuth、me、JWT请求及刷新；管理员列表/详情/筛选/编辑/恢复跟随/停用/审计接口采用字段白名单。
4. 来源仅局部更新，后台编辑校验独立版本，旧来源批次有顺序保护；OAuth返回保存后的最新有效身份。

## 固定约束

- 系统管理员唯一来源为env；主应用、OAuth、回调与安全参数仍由env维护，不开放后台改写。
- 全部用户含未登录通讯录成员，范围受限须明示；来源同步不覆盖人工授权，不把名单缺失当作离职。
- 人工角色替换自动业务角色，env管理员独立；保持各模块既有角色/部门/参与关系组合并明确收敛差异。
- 通知无覆盖使用主应用，错误覆盖不自动改主应用；不把env Secret复制入库。
- 不恢复原专业安全M9，不硬删除用户，不写回企业微信组织，不自动生产部署。

## 验证重点

- 用真实PostgreSQL验证重复同步、后台编辑冲突409、OAuth并发、来源乱序及身份/外键不变。
- 覆盖旧token下一请求生效、人工空角色不补回、平台停用各认证路径一致、env管理员例外及跨企业拒绝。
- 验证无权请求与伪造管理员字段被拒绝；未知历史登录时间不得当作从未登录。

按改动运行必要测试，避免复刻实现的低价值测试。所有新增/删除文档运行inventory生成和索引校验，并执行 `git diff --check`。
