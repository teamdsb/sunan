# 里程碑 9 需求：平台管理与配置升级

## 1. 定位与状态

按用户 2026-11-16 的要求，删除原“专业安全业务深化与体系完善”M9 需求、暂停计划、路线、backlog 和提示词，以本需求重新使用 M9 编号。原专业安全扩展不再是待恢复任务；M7/M8 已完成的实现及历史验收事实保留。

M9-W2 后端、W3 管理后台与业务接入、W4 推送配置与统一发送均已实施并有条件验收；W5 回归与现场验收尚未完成，未生产部署。本文描述目标行为，已实施范围与证据见 [W2](../acceptance/M9-wave-2.md)、[W3](../acceptance/M9-wave-3.md)、[W4 验收](../acceptance/M9-wave-4.md)。下节现状表保留重新规划时的差距快照，不代表这些功能仍未实现。

目标：系统管理员在平台管理全部企业微信成员，调整平台部门与业务权限；用户重新认证和通讯录同步不会覆盖人工设置；推送应用可在后台配置，缺省沿用 env 中的主应用。

入口：[执行计划](../plans/M9-execplans.md) · [Wave backlog](../plans/M9-wave-backlog.md) · [实施提示词](../prompts/README.md)。

## 2. 现状与方案选择

2026-11-16 源码核查：

| 现状 | 影响 | 实施切入点 |
|---|---|---|
| OAuth 登录保存企业微信部门、职位等，业务角色按部门/职位推导 | 直接编辑这些字段会被重新授权覆盖 | `apps/api/src/modules/auth/auth.service.ts`、`role-resolver.service.ts` |
| JWT 后续请求查库计算角色，前端已有用户时跳过身份刷新 | 后端适合下一请求生效，前端菜单和查询缓存仍需刷新 | `auth/strategies/jwt.strategy.ts`、`apps/web/src/layouts/AppShell.tsx` |
| 用户主要随登录入库，无完整通讯录导入和专用用户管理 API | 当前数据库中的用户不等于全部成员 | `database/entities/wecom-user.entity.ts`、`wecom/wecom-http.gateway.ts` |
| 采购、证件提醒、自查候选人等各自读取部门或推导角色 | 只改登录鉴权会造成业务权限与收件人不一致 | `procurement/`、`reminder/`、`workbench/` |
| 证书、采购、任务消息使用同一发送服务，token/锁未按应用隔离 | 独立通知应用可能污染主应用凭据缓存 | `wecom/wecom-message.service.ts`、`wecom-token.service.ts` |

方案比较：直接修改通讯录镜像字段改动少，但重登会覆盖；停止组织资料同步可以保留人工值，但资料会陈旧；**采用“企业微信来源资料 + 平台人工设置 + 统一生效计算”**，保留来源更新，同时明确平台授权优先级。

## 3. 范围

### 本期包含

1. 全部通讯录成员同步，包括从未登录平台的成员；用户已明确确认该范围。
2. 仅系统管理员可访问的用户列表、详情、平台部门和业务角色调整、平台停用/恢复与变更历史。
3. 来源部门与平台部门分离，自动角色与人工角色分离，认证/同步/并发编辑不互相覆盖。
4. 全业务统一有效用户、部门、角色、管理员身份与可用状态；前端及时刷新权限。
5. 后台可选通知应用、凭据保护、配置生效状态、测试发送及投递结果查看。
6. 存量迁移、回滚规则、回归验收与管理员操作说明。

### 本期不包含

- 在平台创建企业微信账号、修改企业微信 UserID/CorpID、写回企业微信部门或新建组织架构。
- 后台授予/撤销系统管理员、任意编辑 env 或展示主应用 Secret。
- 自定义角色设计器、逐按钮授权引擎、全新审批规则编辑器、多企业租户、短信/邮件/Webhook 渠道。
- 原专业安全 M9 的人员资格、高风险作业、设备库存、文件内审等业务扩展。

权限调整复用现有业务角色和各模块既有的角色、部门、参与关系组合规则，只统一有效身份来源；不统一重写所有模块的数据范围。例如总经办现有跨部门查询仍保留，采购部门审批依现有角色规则判断；人工财务部门搭配 shipping 角色时，采购按 shipping 角色判断相应审批资格，按部门过滤的其他接口使用财务部门。Wave 1 应把这些组合逐项列入权限矩阵。平台部门调整不会自动改变船舶任职、任务参与人或其他独立业务关系。

## 4. 用户、部门与权限

### 4.1 身份与管理员边界

- 单企业部署，身份绑定 env 中的 `WECOM_CORP_ID` 与企业微信 UserID；同步和 OAuth 必须匹配到同一用户，保留已有 UUID 和业务外键。拒绝跨企业 token/资料，不能按姓名合并成员。
- `WECOM_SYSTEM_ADMIN_USER_IDS` 是 `system_admin` 的唯一真源。数据库管理员快照不参与授权、数据范围和收件人计算。
- 管理页面只读显示管理员资格及“来源：env”；写 API 使用字段白名单，拒绝 `system_admin`、`isAdmin`、`isSystemAdmin` 等提权输入，不能修改管理员 env。
- env 白名单调整并使所有 API/worker 实例重载后，现有会话与后台收件人计算采用新结果；后台业务角色调整不能撤销 env 管理员的全局权限。

### 4.2 分开保存来源与人工设置

| 数据 | 写入者 | 规则 |
|---|---|---|
| 企业微信姓名、头像、部门 ID/名称、职位、成员状态、同步时间 | OAuth / 通讯录同步 | 仅更新来源字段，不含平台覆盖和人工停用字段 |
| 部门模式 `follow_wecom / manual` 与人工部门 ID 列表 | 系统管理员 | 默认跟随；人工选择使用同步部门字典，支持多部门，不接受自由文本伪造部门 |
| 角色模式 `auto / manual` 与人工业务角色列表 | 系统管理员 | 自动按有效部门计算；人工模式替换自动业务角色，不做叠加 |
| 平台状态 `enabled / disabled`、原因、修改版本 | 系统管理员 | 与企业微信成员状态分开，不会被同步或重新登录恢复 |
| 上次登录、上次同步、同步批次和变更审计 | 相应流程 | 从未登录与同步失败可区分；同步不伪造登录时间 |

本期可设置的业务角色为 `general_office`、`finance`、`business`、`shipping`、`logistics`、`crew`，允许多选。`all_authenticated` 是有效账号的基础身份，不作为可编辑角色；人工空角色列表代表“不授予额外业务角色”，仍保留基础成员能力。彻底禁止使用平台应使用停用。

未设置覆盖与明确设置为空必须能区分。部门模式和角色模式分别保存；“恢复跟随企业微信部门”不隐式清除人工角色，“恢复自动角色”也不隐式改部门。页面保存前展示两者组合后的有效结果。

### 4.3 唯一的生效算法

1. 检查当前企业与已知的企业微信成员状态，明确不可用者拒绝认证和受保护请求；再按 env 判断管理员资格。普通成员检查平台 enabled/disabled；env 管理员不受人工 disabled 限制，避免后台状态成为管理员授权的第二真源。
2. 有效部门 = 人工部门（manual）或最新企业微信部门（follow_wecom），统一解析部门代码与数据范围。
3. 业务角色 = 人工列表（manual）或根据有效部门推导（auto）。仅在部门跟随且角色自动时保留既有职位识别船员的兼容规则；人工部门模式不得从旧企微职位额外补回角色。
4. 对有效账号添加 `all_authenticated`，再独立按 env 判断是否添加 `system_admin`。
5. 登录、`/auth/me`、token 刷新、角色守卫、业务可见范围、审批候选人和通知收件人共用上述结果，不各自补角色。

人工部门为空时不提供基于部门的范围，已有角色直接授予的范围仍按各模块规则判断；未知部门不自动获得业务角色。已人工选择的部门若在后续同步中无法找到，保留设置并标记待核对，不自动回到来源部门或扩大权限。历史单据创建部门、已留存审批人和审计快照不改写；未来操作按现有业务授权规则使用最新有效权限，需交接的未结任务不静默转移。

### 4.4 重新认证、旧会话与并发

- OAuth 重新授权、token 刷新、通讯录批量同步只更新允许的来源资料；人工部门/角色、平台停用状态、审计与用户 UUID 保持。
- OAuth 返回值也从保存后的最新有效授权计算，不能先用来源资料算角色再返回。
- 管理员保存使用独立授权版本进行乐观锁校验，冲突返回 `409`；OAuth/同步只写来源字段，不能将旧整行对象 `save` 回去覆盖人工设置。同步和 OAuth 来源更新需有顺序保护，旧批次不得覆盖更新的来源快照。
- 管理员变更提交后，从下一次受保护请求起生效，不等待 JWT 过期；请求处理中已经开始的事务按原授权完成，不能承诺撤回已发送消息或已执行动作。
- 已停用成员的 OAuth、`/me`、旧 token 访问、token 刷新均被拒绝；不能仅隐藏按钮。恢复平台状态不绕过已确认的企业微信不可用状态。
- env 管理员不可在后台被平台停用，避免绕过“管理员设置只走 env”。若普通成员曾被停用、后来由 env 提升为管理员，其人工 disabled 保留但暂不生效，页面明确显示；将来从 env 撤销管理员后，该状态重新适用。已确认的企业微信账号不可用仍适用于管理员。
- 前端在恢复页面/重新聚焦时刷新 `/auth/me`，收到权限类 `403` 时更新身份与相关业务缓存；身份不可用时清理会话。后台修改本人成功后立即更新。避免反复刷新造成请求循环。

## 5. 全通讯录同步与管理体验

- 管理范围包括当前企业全部通讯录成员，含从未登录者及历史已登记成员。使用主应用 env 的身份读取企业微信通讯录；独立通知应用不参与认证或组织同步。
- 递归处理部门与多部门成员、分页、去重、失败重试；按身份幂等 upsert。提供管理员手动同步，首期不强制增加定时/事件同步；重新授权继续更新当前成员的来源资料。
- 同步显示批次、状态、起止时间、可见部门、读取/新增/更新/失败数量、上次成功时间。状态至少区分进行中、成功、部分成功和失败；重复触发合并或明确提示正在同步。
- 应用可见范围或通讯录读取权限不足时，显示“当前仅覆盖应用可见范围”，不得把已取到的用户数称为全企业总人数。无法证明全量覆盖时显示“完整性未验证”；全目录验收以主应用确实可读取全企业目标成员为前置，并与企业微信管理员核对；局部可用或完整性未验证不能算“全部通讯录成员”验收通过。
- 部分失败、分页未完成、查不到某成员或应用可见范围缩小不等于离职，不能据此自动删除/停用或清除覆盖；只有明确可靠的成员不可用信息才更新其来源状态。已有数据保留并显示来源时间。
- 同步不能使平台人工停用的用户恢复，也不能只凭名单缺失禁用管理员。已确认离职/禁用成员保留历史记录、停止新授权和新收件；不硬删除用户。
- 分页列表支持姓名/UserID 搜索，以及有效部门、业务角色、env 管理员、平台状态、是否登录、是否人工覆盖筛选。默认可找到全部状态用户，标明当前筛选与总数口径。
- 详情对照展示企微来源与平台生效值、授权模式、登录/同步时间、状态和变更历史；不直接返回完整 `rawProfile` 或无关敏感信息。
- 部门/角色/状态修改填写原因，保存前预览有效结果，保存后显示成功或明确错误；停用、恢复跟随与撤销业务角色需要展示影响。首期逐人编辑，不加批量授权。
- 延续四大业务入口，在已有系统设置中增加“用户管理”“消息推送”；支持桌面与 H5 的分页、搜索、详情、错误、空态和无权限反馈。

## 6. 配置归属与缺省规则

### 6.1 配置白名单

| 配置 | 唯一来源 | 后台能力 |
|---|---|---|
| 系统管理员 UserID 白名单 | env：`WECOM_SYSTEM_ADMIN_USER_IDS` | 只读显示资格来源，不可授予/撤销 |
| 主应用企业 ID、AgentID、Secret | env：`WECOM_CORP_ID`、`WECOM_AGENT_ID`、`WECOM_AGENT_SECRET` | 可显示必要的非敏感标识与配置状态，Secret 不返回 |
| OAuth/事件回调、Token、AESKey、签名/IP/时差配置、JS-SDK 及部署域名 | env：现有 `WECOM_*`、`WEB_PUBLIC_URL`、`API_PUBLIC_URL` 等 | 无编辑入口；现有生产安全校验继续生效 |
| 可选消息推送应用 | 数据库：同企业通知应用 `AgentID + Secret` | 可填写、验证、保存、替换、清除；CorpID 固定继承主应用 |
| 后台凭据加密主密钥 | 新增 env，拟名 `SYSTEM_SETTINGS_ENCRYPTION_KEY` | 不展示、不编辑；支持加密版本/轮换方案 |
| DB/Redis/JWT/OSS、端口、环境、监控、备份、发布开关 | 继续 env / 部署配置 | 本期不迁入后台 |

本期先开放可选推送应用，其他后台配置以后逐项按白名单评估，不建立任意键值写 env 的入口。默认不需要填写独立推送配置。

### 6.2 通知应用解析

| 后台已保存状态 | 运行规则 |
|---|---|
| 尚未设置或已明确清除覆盖 | 使用 env 主应用的完整 CorpID + AgentID + Secret |
| 独立应用 AgentID + Secret 完整 | 使用同企业独立通知应用的完整配置 |
| 首次仅填写 AgentID 或 Secret | 拒绝保存，不改变现有配置 |
| 编辑时 Secret 留空 | 保留已存 Secret；更换 AgentID 必须重新填写匹配 Secret |
| 显式覆盖存在但鉴权失败、应用不可见、解密失败或读取配置失败 | 显示并记录失败；不得静默解释为空配置或换主应用重发 |

清除覆盖是独立操作，删除凭据并提交新的配置版本后恢复主应用。主应用 Secret 与独立 Secret 不可拼接混用。独立应用只发送消息；OAuth、回调、通讯录、JS-SDK、现有审批/媒体等主应用调用始终走 env 主应用。

### 6.3 凭据与配置生效

- 独立 Secret 使用认证加密入库，密文携带算法/密钥版本；加密主密钥独立走 env，不能复用 JWT/主应用 Secret。迁移不把 env Secret 拷入数据库。
- API 仅返回 `hasSecret`/配置状态与必要非敏感标识，不返回明文或可还原 Secret；请求、日志、审计和错误链路均脱敏，审计只记录变更字段、来源、版本和操作者。
- 未配置独立应用且无加密主密钥时仍可使用主应用推送，但禁止保存独立 Secret；已有覆盖无法解密时必须显示故障，不能静默回退。轮换须有重新加密、备份密钥和恢复步骤。
- 整组配置原子提交，携带版本，防止多个管理员互相覆盖；失败返回明确错误且旧配置仍有效。多实例读取不得长期保留旧配置，保存后新投递按新提交版本解析。
- token、刷新锁和相关缓存按企业/应用/配置版本隔离；只刷新失效应用，独立推送应用不能污染主应用 token/ticket。清除覆盖也递增版本，避免复用旧凭据缓存。
- “验证连接”与“测试发送”分开：拿到 token 只证明凭据可用，不能证明 AgentID/接收范围正确。测试消息只发送给管理员明确选定的测试接收人，不发全员；未保存草稿测试不改变线上配置。

### 6.4 推送链路与故障可见

- 证书/合同提醒、采购审批与报表通知、计划任务分派/转移/催办/逾期都经统一通知配置解析发送，保留各自业务触发与去重规则，不让消息改变业务状态。
- 收件人统一使用有效部门/角色与当前账号状态，发送前重新核验。人工指定且仍有效的历史参与人不因改部门被自动替换；失去资格或已不可用的对象不得继续获得超出当前授权的消息内容。
- 每次发送尝试记录业务来源、接收人、实际应用、配置来源与版本、时间、结果和脱敏错误。复用任务的持久化投递机制，为采购等仅有日志的链路补足最小结果查询，不另建完整营销消息平台。
- 一次外部发送采用同一份配置快照；处理中不换应用。失败重试沿用原业务去重键，重新解析当前配置并记录新尝试来源；已成功消息不因修改配置重发。发送结果不确定时保留待核对状态，补充可查询记录与人工核对/处理入口，未经核对不得自动跨应用重试；采购等尚无对账能力的链路必须补齐此最小机制。
- 显式配置失败、目标不在应用可见范围、限流和网络失败可查询，并给出可执行的修复/重试说明；URL 继续使用受控主应用地址，消息链接不授予业务权限。

## 7. 数据迁移与回滚

- 保留现有 `wecom_users` UUID、单企业 UserID 及业务外键；先检查 corp 归属和重复/异常身份，不把本期变成多租户改造。
- 存量来源资料作为初始快照，部门默认 follow_wecom、角色默认 auto、平台默认 enabled；登录业务角色保持迁移前兼容，不能因迁移扩大权限。各业务现有旁路推导差异单独形成收敛清单，按统一规则核对影响，不复制已有的不一致授权。例如部门 8 的登录角色为 crew，提醒模块却可能从 shipping_dept 再补 shipping；该差异必须有明确的范围核对及回归证据。
- 历史成员状态若缺少可靠证据，标记未知并等待同步核对，不批量推定离职。历史没有真实登录时间的记录显示“未知”，不能用 createdAt 伪造“从未登录”。后续新增的纯同步成员才可明确标记从未登录。
- 平台授权与来源更新分离，增加独立授权版本及审计；部门字典、同步批次、配置和投递字段按关系化需求设计，Wave 1 冻结实际表名与兼容策略。
- 新增配置默认无覆盖，因此现有 env 主应用继续工作；不自动改动任何真实 env 值、管理员白名单或业务角色。
- **启用人工覆盖/停用后，不能直接回滚到忽略这些字段的旧程序。** 上线前准备同时识别新授权规则、通知配置/加密与投递约束的兼容版本；若无法兼容，则维护窗口暂停访问及相关推送入口/worker，导出/备份人工设置并核对配置影响后处理，不以静默丢弃覆盖恢复旧权限或改用主应用发送。
- 发布备份包括用户授权、配置密文、审计与必要的密钥恢复材料；密钥与数据库备份分开受控。配置回滚以历史内容创建递增的新版本，不回退版本号；保留原去重键和发送历史，避免复用旧缓存或补发重复消息。

## 8. 核心验收场景

| 编号 | 场景 | 通过条件 |
|---|---|---|
| U1 | 未登录成员同步与重复同步 | 全企业目标成员可查并核对覆盖，稳定身份不重复、不丢外键；局部或完整性未验证不算全目录验收通过 |
| U2 | 可见范围不足/中途分页失败 | 显示范围/失败数量，不删除或批量禁用缺失成员，不清人工设置 |
| U3 | 管理员改部门/角色后 OAuth、刷新、同步 | 人工设置保持，返回最新有效身份；恢复跟随后才采用来源 |
| U4 | 明确空业务角色、人工部门与旧职位冲突 | 不从来源部门/职位补回角色；基础成员权限仍按现有规则保留 |
| U5 | 旧 token、本人调整、跨页面权限 | 下一请求执行新权限，前端刷新身份/缓存，无越权或刷新循环 |
| U6 | 并发后台编辑、OAuth 与同步乱序 | 后台冲突 409；来源更新不覆盖人工字段、旧批次不回写旧快照 |
| U7 | 非管理员、伪造管理员字段、env 撤权 | 管理 API 拒绝越权；所有实例重载 env 后管理员识别与通知范围一致 |
| U8 | 平台停用/恢复、已知企业成员不可用 | OAuth、me、刷新、旧 token 与收件人统一校验；env 提升/撤销与既有 disabled 组合无冲突 |
| U9 | 采购、自查、提醒、企业资料、任务与学习选择器 | 有效身份口径一致，历史快照不改写，不扩大船舶/参与人范围 |
| C1 | 无配置、半配置、保留 Secret、清除覆盖 | 完整主应用缺省；半配置拒绝；空白保留；明确清除才回主应用 |
| C2 | 独立应用与主应用并行 | 三类业务消息用指定应用，登录/SDK/回调仍用主应用，缓存/锁隔离 |
| C3 | 错密钥、错误应用、不可见接收人、配置读取失败 | 失败可查，不静默回主应用；验证连接与测试发送结论不混淆 |
| C4 | 配置并发、轮换、多实例、失败重试 | 一次发送配置一致，新尝试记录版本，成功消息不重推，无明文泄漏 |
| R1 | 存量迁移与兼容回滚 | 登录角色基线兼容，业务旁路差异按收敛清单核对；授权/通知设置与密钥可恢复，旧程序不绕过覆盖 |

自动化使用仓库 PostgreSQL 集成环境验证真实并发、唯一约束和事务；只为这些风险编写必要测试，不为文档或字段映射复制测试。企业微信真实范围、真实独立应用送达和 H5 三端由现场记录实际结果，未执行不得写成通过。

## 9. 交付与执行顺序

W1 契约与迁移冻结 → W2 用户目录及授权后端 → W3 管理后台与业务接入 → W4 推送设置与发送整合 → W5 迁移回归与验收。W4 的配置后端可在 W1 冻结后与 W2 并行，最终收件人整合依赖 W2/W3。

每个 Wave 有独立范围、前置、退出条件和验收记录；计划和提示词见本文入口。功能实施阶段只更新必要的 common/auth、notification、wecom 契约和操作手册，不把未实施的目标批量写入现行规格或手册。
