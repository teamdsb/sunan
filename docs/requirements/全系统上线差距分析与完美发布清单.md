# 全系统上线差距分析与完美发布清单

## 1. 文档定位

本文基于以下输入进行综合判断：

- 原始总需求：`docs/需求文档.md`
- 里程碑需求：`docs/requirements/M1-我的.md`、`M2-办事.md`、`M3-采购管理.md`、`M4-工作平台.md`、`M5-上线强化与遗留收口.md`
- 非功能需求：`docs/requirements/非功能需求.md`
- 工作平台与企业微信专项规格：`docs/specs/workbench/*`、`docs/specs/wecom/*`
- 当前系统实现：`apps/web`、`apps/api`

本文不替代执行计划，也不重写历史验收结论；目标是给出一份“现在距离全量上线还差什么”的统一结论，并明确“快速上线”和“完美上线”两种口径的差别。

## 2. 结论摘要

### 2.1 当前真实状态

当前系统已经具备以下上线基础：

- `我的`、`办事`、`采购管理` 三大板块具备独立路由、前后端模块和自动化测试基础。
- `工作平台` 已完成统一底座、运行时持久化、审批桥、统计导出/对账接口和上线文档模板。
- 企业微信 OAuth2、JS-SDK、消息、审批桥、文件上传、打印快照、审计日志已有可运行基础。

但如果以 `docs/需求文档.md` 中的“四大板块全量完成”作为标准，当前系统还不能定义为“完美上线发布”。最大的差距不在基础设施，而在 `工作平台业务模块本体` 仍未按原始需求完成高保真实现。

### 2.2 一句话判断

- 若按“第一批可投产范围”判断：可以组织 `我的 + 办事 + 采购管理 + 工作平台底座能力` 的试运行或受控上线。
- 若按“总需求文档全量兑现”判断：暂时不能宣布完美上线，必须继续完成工作平台业务模块全量落地、遗留模块补齐、企业微信生产配置与真机证据闭环。

## 3. 按板块的完成度判断

| 板块 | 当前判断 | 说明 |
|---|---|---|
| 我的 | 基本完成 | 路由、前后端模块、提醒、设置、文件绑定都已成型，可进入正式环境验证 |
| 办事 | 基本完成 | 门户、搜索、治理台、审计链路已成型，主要差距在生产配置和真机/UAT 留痕 |
| 采购管理 | 基本完成 | 录单、审批、报表、字典治理、打印链路已具备，需补生产模板、业务口径确认和上线材料 |
| 工作平台底座 | 已完成 M5 主线 | 运行时落库、审批桥、统计导出/对账、日志留痕、测试基线已到位 |
| 工作平台业务模块 | 未完成 | 当前只有通用工作平台页和模板化 schema，未完成原始需求中的大批模块级高保真实现 |
| 企业微信上线材料 | 未闭环 | 检查清单与模板已具备，但生产参数、模板编码、真机证据、值班与回滚材料仍需实际补齐 |

## 4. 仍未真正实现的功能需求

## 4.1 工作平台仍是“统一底座”，不是“全量业务模块”

原始需求和 M4 需求要求工作平台完成总经办、财务部、业务部、船务部、后勤部、工作组的大量具体业务模块；但当前前端路由只有一个工作平台首页：

- `apps/web/src/router/workbenchRouteConfig.ts`
- `apps/web/src/router/AppRoutes.tsx`
- `apps/web/src/features/workbench/WorkbenchHomePage.tsx`

这说明当前工作平台前端还处在“通用首页 + 通用列表/详情/动作”的阶段，尚未形成每个模块对应的独立页面、模块化交互和高保真录单界面。

尚未完成为真正业务成品的模块，至少包括：

- 总经办：培训管理、会议管理、安全月活动、安全隐患排查管理、年度工作计划
- 财务部：统计中心的完整业务化页面、财务板块
- 业务部：作业人员签到台、接收工作组操作流程、围油栏、签船记录表、船舶动态记录表、垃圾/污油水/生活污水接收
- 船务部：船员培训学时统计、船舶自查排查、船员考勤、设备保养、船舶检验、演练系统、密闭空间、值守记录、岸基叫应、会议记录、污油水接收作业、海事安检、案例警示学习、航次计划审批、燃油加注
- 后勤部：仓库、办公室、食堂、宿舍、车辆维修保养
- 工作组：中船工作组、平陆运河工作组五步作业闭环

## 4.2 高保真字段仍未补齐，现有 schema 还是“模板级最小实现”

当前后端虽然注册了大量模块，也提供了模板化 schema，但很多字段仍明显低于原始需求的高保真程度，典型位置在：

- `apps/api/src/modules/workbench/workbench.service.ts`
- `docs/specs/workbench/ui/workbench-department-modules.md`

例如：

- `签船记录表` 原始要求包含客户姓名、船型、总吨、收费方式、泊位、装货类型、带班领导、签订日期、值守船舶等；当前 schema 只覆盖其中一部分。
- `岗前培训` 原始要求包含学习进度查看、培训完成审批；当前 schema 仍偏台账录入，不是完整培训业务流。
- `统计中心` 原始要求包含手机打卡、钦州市区范围定位、上午/下午、出差/外派、作业票和劳务费统计；当前 M5 落地的是统一统计接口和导出/对账底座，不等于完整财务业务页面。

换言之，`工作平台已具备“能录、能存、能审、能打”的底层能力，但还没有达到“原始业务表单 1:1 还原”的完成度。`

## 4.3 财务板块仍未实现

`财务板块` 在当前文档体系中的状态仍然是：

- 已纳入边界
- 未冻结字段级 API
- 未冻结表结构
- 未见前后端独立实现

相关依据：

- `docs/specs/workbench/db/workbench-module-matrix.md`
- `docs/specs/workbench/ui/workbench-department-modules.md`
- `docs/requirements/M5-上线强化与遗留收口.md`

这意味着财务部在原始总需求中的一个独立业务板块，目前仍属于“待业务继续补资料后开发”的状态。

## 4.4 海图更新仍未实现

`海图更新` 已在 M5 被纳入边界，但当前仍然只是“最小规格冻结”，尚未看到独立实现：

- 已知边界：更新批次、适用船舶、版本/日期、说明、附件、确认记录
- 未见独立页面、独立 API、独立实体和独立测试

相关依据：

- `docs/specs/workbench/db/workbench-module-matrix.md`
- `docs/specs/workbench/ui/workbench-department-modules.md`

## 4.5 工作平台管理员运维前端还没接起来

M5 后端已经补齐了审批异常检索、重试、对账，以及考勤导出/对账接口：

- `apps/api/src/modules/workbench/workbench-approval.controller.ts`
- `apps/api/src/modules/workbench/workbench.controller.ts`

但当前前端 `apps/web/src/features/workbench/workbenchApi.ts` 只接了：

- 模块列表
- schema
- dashboard
- 记录列表/详情/动作
- 审批发起
- 基础统计查询

还没有看到以下能力的前端页面或接线：

- 审批实例异常检索
- 单实例重试
- 管理员对账
- 月统计导出任务
- 财务对账操作页

这意味着 `M5 后端运维能力已具备，但工作平台管理后台还未完整落前端`。

## 5. 还需要补充的内容

## 5.1 业务与规格补充

要把总需求真正做完，至少还需补齐以下业务输入：

- `财务板块` 的业务目标、角色、字段、流程、导出和审批边界
- `海图更新` 的原始样表、字段样例、确认动作和打印要求
- 工作平台各模块的真实表单样张、纸质记录本、拍照样例、审批链说明
- 模块与企业微信审批模板的正式映射表
- 各统计口径的业务确认稿，尤其是考勤、劳务费、油耗、培训学时

如果这些资料不补齐，开发会继续停留在“模板化近似实现”，无法达到业务方期待的高保真。

## 5.2 系统实现补充

从代码层面，下一批必须补的不是基础设施，而是业务完成度：

- 为工作平台各大模块建立独立页面、独立交互和独立打印模板
- 将当前模板化 schema 升级为高保真字段模型
- 补齐工作平台管理员端页面：审批诊断、重试、对账、导出、异常处理
- 补齐消息提醒、待办聚合和审批状态在前端的闭环展示
- 为高频模块补录批量操作、归档、查询和筛选体验

## 5.3 上线运维补充

要进入真正生产发布，还需要补齐以下交付物：

- 企业微信生产应用参数、可信域名、回调域名、JS-SDK 域名的最终登记
- 审批模板编码清单、模板截图、模板负责人
- 真机回归结果表、截图/录屏证据、缺陷闭环单
- 日志看板、告警项、值班人、故障升级路径
- 数据备份/恢复方案、回滚预案、上线窗口操作手册
- 初始化数据清单：组织角色、船舶、车辆、基础字典、管理员名单

当前这些内容在文档模板里已经定义，但还不是“已完成交付物”。

## 6. 怎样才能做到“完美上线发布”

## 6.1 先统一发布口径

必须先明确到底追求哪一种上线：

- `口径 A：受控上线`
  只上线已成型模块：`我的`、`办事`、`采购管理`、`工作平台底座`
- `口径 B：工作平台一期上线`
  在底座之上再上线一批真正高频的工作平台模块
- `口径 C：总需求完美上线`
  按 `docs/需求文档.md` 覆盖四大板块全部核心业务

如果目标是“完美上线”，就不能只看 M5 是否完成，而要看 `M4 工作平台业务本体是否全量交付`。

## 6.2 完美上线的必做条件

建议按以下顺序推进：

1. 完成工作平台业务模块第一批高频模块
   建议优先做：`签船记录表`、`船舶动态记录表`、`作业人员签到台`、`接收工作组操作流程`、`船员考勤`、`值守记录系统`

2. 完成遗留模块收口
   补齐 `财务板块` 和 `海图更新` 的真实业务资料与字段规格，再进入开发

3. 完成管理员运维台
   把 M5 后端已有的审批异常检索、重试、对账、统计导出接成前端页面

4. 完成企业微信生产联调
   包括 OAuth2、JS-SDK、审批模板、消息模板、回调、应用可见范围、iOS/Android 真机回归

5. 完成上线材料包
   至少包括：配置截图、真机报告、缺陷闭环、回滚预案、值班联系人、审批模板清单、告警项清单

6. 完成业务 UAT 签字
   每个部门至少确认：字段正确、流程正确、打印正确、统计正确、权限正确

## 6.3 推荐的实际落地策略

最稳妥的方式不是继续泛化开发，而是分两阶段：

- 第一阶段：正式上线已成熟范围
  即 `我的 + 办事 + 采购管理 + 工作平台底座 + 部分高频工作平台模块`

- 第二阶段：补齐工作平台全量模块与遗留模块
  把 M4 Wave 3 ~ Wave 7 的业务模块真正做成，并将 `财务板块`、`海图更新` 收口

这样既能尽快上线见效，也不会把“底座已完成”误判成“全部业务已完成”。

## 7. 最终判断

从当前文档和代码综合看，系统已经走到了“可以组织首批上线”的阶段，但还没有走到“总需求文档已全量兑现”的阶段。

决定是否可以宣布“完美上线发布”的关键，不再是 M5 的稳定性建设，而是以下三件事是否真正完成：

- 工作平台业务模块是否从模板化底座升级为高保真业务成品
- `财务板块` 与 `海图更新` 是否从边界文档进入真实实现
- 企业微信生产配置、真机证据、上线材料是否全部闭环

如果这三件事没有完成，系统适合定义为“首批正式上线”或“分阶段上线”，不适合定义为“全量完美上线”。
