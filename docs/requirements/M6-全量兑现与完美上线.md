# 里程碑 6 需求文档：全量兑现与完美上线

## 1. 文档定位

本文件定义里程碑 6 的执行型需求，用于把当前系统从“已具备首批上线基础”推进到“总需求文档全量兑现、工作平台高保真业务成品、企业微信正式发布闭环”。

M6 不再以“补底座”为主，而是以以下三件事为主线：

- 将 `docs/需求文档.md` 中尚未兑现的业务本体补成可验收交付。
- 将工作平台从“统一 schema 壳层”升级为“独立模块页面 + 通用运行时”的高保真形态。
- 将企业微信从“已有专项文档模板”推进到“生产配置、真机证据、UAT、回滚和值班均闭环”的正式发布状态。

## 2. 当前代码与交付现状

### 2.1 已接近正式交付的范围

- `我的`：具备独立前后端模块、提醒、设置、文件上传与测试基线。
- `办事`：具备统一入口、搜索、治理台和企业微信内访问基础。
- `采购管理`：具备录单、审批、报表、字典治理、打印导出与自动化测试基础。
- `工作平台底座`：已具备模块注册、统一记录运行时、审批桥、审批回调、导出/对账接口、持久化实体和集成测试基础。

### 2.2 当前最大差距

结合 `docs/requirements/全系统上线差距分析与完美发布清单.md` 与当前代码：

- 前端工作平台仍以 `/workbench` 单一路由和通用 schema 驱动壳层为主，尚未形成模块级独立页面。
- 后端虽然已具备大量 `moduleCode + schema + runtime`，但多数模块仍是“模板化最小实现”，尚未达到原始样表还原度。
- `财务板块` 与 `海图更新` 仍停留在遗留边界或最小边界，没有进入完整 SDD。
- 审批异常检索、重试、对账、导出、诊断能力以后端接口为主，缺少成型的管理员控制台规格。
- 企业微信已有 OAuth2、JS-SDK、消息、审批桥与上线检查文档，但生产参数、模板映射、真机证据、回滚和值班尚未完成实际闭环。

### 2.3 M6 的现状判断

当前系统可以组织“成熟模块受控上线”，但还不能定义为“总需求文档全量兑现与完美上线”。M6 必须解决的是“业务完成度”和“正式发布闭环”，而不是再次泛化平台底座。

## 3. M6 目标与原则

### 3.1 主目标

- 让 `docs/需求文档.md` 中四大板块达到可验收的全量兑现状态。
- 将工作平台升级为“独立页面 + 模块元数据 + 通用运行时 + 管理员运维台”的正式形态。
- 完成 `财务板块` 的 provisional SDD 与 `海图更新` 的正式 SDD，纳入 M6 实施与验收范围。
- 冻结企业微信正式发布所需的 OAuth2、JS-SDK、审批、消息、回调、真机、UAT、回滚和值班规格。

### 3.2 实施原则

- 不重写 M1-M5 基础文档，只增量更新 M6 直接依赖文档。
- 不把工作平台拆成几十个独立后端模块，继续保留统一 bounded context、统一运行时和统一审批桥。
- 规格优先于实现，先冻结模块路由、页面组、字段组、动作、打印和审批映射，再进入开发。
- 对缺少样表支撑的模块，不伪装成已确认需求；必须显式标记 `provisional` 或 `待确认`。

## 4. M6 范围

### 4.1 纳入范围

#### 4.1.1 工作平台独立页面化

- 冻结以下前端路由：
  - `/workbench`
  - `/workbench/modules/:moduleCode`
  - `/workbench/modules/:moduleCode/new`
  - `/workbench/modules/:moduleCode/:recordId`
  - `/workbench/admin/approvals`
  - `/workbench/admin/exports`
  - `/workbench/admin/reconcile`
  - `/workbench/admin/diagnostics`
- `GET /workbench/modules/:moduleCode/schema` 继续保留，但职责调整为“页面元数据与共享字段定义”，不再承担完整动态页面渲染。

#### 4.1.2 工作平台高保真模块化

- 高频模块 Batch A：
  - 总经办：岗前培训、会议管理、安全月活动、年度工作计划
  - 业务部：签船记录表、船舶动态记录表、作业人员签到台、接收工作组操作流程、围油栏、垃圾/污油水/生活污水接收
  - 船务部：培训学时、演练、值守、岸基叫应、船员会议记录、案例警示学习
  - 工作组：中船、平陆运河五步作业闭环
- 高风险模块 Batch B：
  - 总经办：安全隐患排查
  - 船务部：船舶自查排查、船舶检验、密闭空间、污油水接收作业、海事安检、船员考勤、航次计划审批、燃油加注
  - 财务部：统计中心
  - 后勤部：仓库、办公室、食堂、宿舍、车辆维修保养

#### 4.1.3 遗留模块收口

- `财务板块`：先输出 provisional SDD，明确页面范围、角色、入口、与统计中心的关系、导出包、审批边界和待确认项。
- `海图更新`：升级为正式 SDD，明确批次、适用船舶、版本/日期、更新资源、附件、确认记录、打印归档，以及与现有 `chart_update` 提醒类型的联动规则。

#### 4.1.4 管理后台与运维闭环

- 新增工作平台管理员台规格：
  - 审批实例检索、单实例重试、批量对账
  - 导出任务查询、失败重试
  - 审批失败、消息失败、JS-SDK 签名失败、导出失败的诊断事件查询
- 新增 `workbench-admin-api.yaml`，承载管理员台独有接口。
- `workbench-approval-api.yaml` 增补管理员查询维度：`dateFrom`、`dateTo`、`syncErrorCode`、`source`。

#### 4.1.5 企业微信正式发布闭环

- OAuth2、可信域名、JS-SDK、审批回调、消息回调、应用可见范围、审批模板映射、消息模板映射。
- iOS / Android 企业微信真机回归。
- 发布材料、回滚预案、值班机制、联系人清单。
- JS-SDK 规格按官方当前推荐 `@wecom/jssdk` / `ww.register` 设计，同时保留 legacy adapter 作为灰度兼容。

### 4.2 不在 M6 范围

- 新增第五大业务板块。
- 引入预算平台、供应商主数据平台、BI 大屏等新业务域。
- 对 `docs/architecture/*`、`M1-M5 requirements`、`common specs` 做重写式改造。
- 在没有原始样表支撑的前提下为 `财务板块` 发明字段、流程或报表口径。

## 5. M6 波次规划

### Wave 1：M6 文档重构与现状审计

- 重写 M6 需求、主执行计划、工作平台 README 与模块矩阵。
- 逐模块写清：原始需求来源、当前代码现状、M6 页面形态、阻塞项。
- 将 `财务板块`、`海图更新` 升级为独立 SDD 入口。

### Wave 2：企业微信运行时与上线规格冻结

- 冻结 JS-SDK 迁移规格、OAuth2/可信域名/回调/审批/消息生产配置口径。
- 更新 `docs/specs/wecom/jssdk-spec.md`、`docs/guides/wecom-dev-setup.md`、`docs/specs/wecom/workbench-go-live-checklist.md`。
- 明确灰度方案、回退方案和真机验证门槛。

### Wave 3：工作平台独立页面化与管理员台规格冻结

- 冻结模块路由图、页面信息架构、共享壳层、筛选器与列表/详情/动作分工。
- 冻结管理员控制台 IA、状态模型、API 契约与留痕模型。
- 明确哪些模块只复用统一运行时，哪些模块需要专属页面与专属打印模板。

### Wave 4：高频模块 Batch A

- 批量冻结台账类和作业闭环类模块的字段组、页面组、关键动作、打印模板和归档要求。

### Wave 5：高风险模块 Batch B

- 冻结检查整改类、统计类、审批类、资产服务类模块。
- 同步冻结管理员台依赖的审批实例、导出任务、对账任务与诊断事件规格。

### Wave 6：遗留模块与跨域收口

- 输出 `财务板块` provisional SDD。
- 输出 `海图更新` 正式 SDD。
- 冻结“海图更新完成一次后如何推导下一次半年提醒”的数据规则。

### Wave 7：测试、UAT、上线材料与完美上线验收

- 补齐 OpenAPI 校验、模块级测试矩阵、真机回归矩阵、UAT 模板、缺陷闭环、回滚预案和值班机制。
- 将“完美上线”改写为可执行的发布门槛清单。

## 6. 依赖 Gate

以下事项必须在进入开发或发布前完成：

### 6.1 业务输入 Gate

- 高频模块必须有原始样表、记录本、打印样张或业务确认稿。
- `财务板块` 未经业务确认的字段必须标记为 `provisional`，不得伪装为已确认字段。
- `海图更新` 必须补齐“更新资源信息”与“确认动作”说明后再开发。

### 6.2 企微发布 Gate

- 可信域名、OAuth2 回调域名、JS 接口安全域名、审批回调地址、消息回调地址全部登记。
- `moduleCode -> templateCode -> wecomTemplateId` 映射表冻结。
- 消息模板负责人、审批模板负责人、值班负责人明确。

### 6.3 测试 Gate

- 所有新增/更新 OpenAPI 通过 `swagger-cli validate`。
- 相关 README 状态表与 execplan wave 同步更新。
- 真机回归模板、UAT 模板、缺陷模板先于正式联调冻结。

## 7. 完成定义

### 7.1 高保真业务成品

某工作平台模块只有同时满足以下条件，才算 M6 完成：

- 字段组与原始需求、纸质样表、记录本或业务确认稿一致。
- 具备独立模块页，而不是只依赖通用 schema 壳层。
- 支持真实查询、筛选、详情、动作、附件、打印和归档。
- 审批、消息、待办、统计与权限表现一致。
- 通过模块级测试、业务 UAT 和真机抽检。

### 7.2 完美上线

系统只有同时满足以下条件，才可定义为“完美上线”：

- `docs/需求文档.md` 四大板块无未兑现核心功能。
- 工作平台模块达到高保真业务成品标准。
- `财务板块`、`海图更新` 不再停留在边界文档。
- 企业微信生产参数、审批模板、消息模板、真机证据、回滚预案和值班机制闭环。
- 自动化测试、关键链路冒烟、业务 UAT、正式发布验收均通过。

## 8. 测试与上线要求

### 8.1 规格测试

- 新增/更新 OpenAPI 先校验，再进入实现。
- 规格变更必须同步 README 状态表、execplan wave 和相关 acceptance 文档。

### 8.2 自动化测试

- 为管理员台补审批实例检索、重试、对账、导出任务、诊断事件集成测试。
- 为 `海图更新` 补记录、附件、确认、提醒联动测试。
- 为 `财务板块` provisional 接口补契约测试，明确 `confirmed` / `provisional` 边界。
- 前端新增路由级测试，覆盖独立模块页与管理员页。

### 8.3 真机与 UAT

- 企业微信 iOS / Android 回归必须覆盖 OAuth2、JS-SDK、附件、审批、导出、打印、管理员诊断。
- 每个部门至少完成 1 组字段/流程/打印/UAT 样例确认。
- 海图更新必须补“半年提醒联动”抽检。

### 8.4 发布门槛

- 无 P0 缺陷。
- 所有 P1 缺陷有关闭结论或发布前规避方案。
- 企业微信生产参数、审批模板、回调验证、真机证据、回滚预案、值班联系人齐备。
