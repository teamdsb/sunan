# 苏南船舶管理系统与航运安全管理数字化平台功能对比及升级建议

## 1. 文档目的

本文对比以下两个平台：

- 参考平台：`docs/handbook/航运公司安全管理数字化平台PC、小程序端操作手册.md`
- 苏南平台：当前需求、规格以及 `apps/api/src`、`apps/web/src` 的实际实现

目标不是逐页复制参考平台，而是回答四个问题：

1. 苏南平台已经具备哪些同类能力？
2. 哪些只是通用表单承载，还没有形成专业安全管理闭环？
3. 缺少哪些关键功能、规则和移动作业能力？
4. 如何利用苏南现有企业微信、采购和工作平台基础，分阶段补齐能力？

本报告是 2026 年 6 月 13 日的实现审计快照，不代表后续版本状态。

## 2. 结论摘要

### 2.1 总体判断

苏南平台已经形成企业微信 H5 统一入口，并拥有企业资料、制度、证照、提醒、办事、采购和约 41 个工作平台模块。其覆盖面已经触及参考平台的大部分安全业务名称，但两者目前不是同一成熟度：

- 参考平台的核心是专业航运安全管理体系，强项是专用数据模型、跨模块联动、多人检查、计划任务化、不符合项闭环、内审和监管协同。
- 苏南平台的核心是企业综合工作平台，强项是企业微信工作台、原生审批桥接、统一入口、采购闭环和通用模块快速配置。
- 苏南现有工作平台可作为升级底座，但“存在一个同名模块”不等于“已实现参考平台的完整功能”。

要达到参考平台同等或更好的业务能力，苏南需要从“动态表单加通用步骤”升级为“通用流程底座加安全领域引擎”。

### 2.2 最优升级方向

不建议把苏南改造成参考平台的页面复制品。建议保留以下优势：

- 企业微信工作台独立深链
- 企业微信 OAuth 和原生审批
- H5 一体化体验
- 采购与后勤现有闭环
- 工作平台动态模块目录

在此基础上补齐：

- 船舶、人员、设备、检查项和证书等安全主数据
- 计划、任务、检查、问题、不符合、纠正措施、验证的统一闭环
- 多人签认、责任人、复核人和船舶级数据权限
- 移动拍照、定位、签名、离线草稿和统一待办
- 文件变更、内审、应急、维修备件和监管平台集成
- 可追溯统计、导出、PDF 水印和审计证据

## 3. 评价口径

| 状态 | 定义 |
|---|---|
| 已实现 | 当前前后端存在可操作、可保存、可查询的专用能力，主要业务链路可完成 |
| 部分实现 | 已有同类模块，但缺少关键步骤、专业字段、权限、联动或归档能力 |
| 可配置承载 | 通用表单或流程能记录部分信息，但没有专用模型和业务规则，不应视为等价实现 |
| 缺失 | 当前没有对应的可用功能，或只有需求名称而没有实际用户链路 |
| 定位差异 | 产品形态不同，不宜一比一复制，需要采用企业微信 H5 的等效方案 |

审计原则：

1. 以实际前端能完成的操作为准。
2. 后端存在接口但前端没有入口，最多评为部分实现。
3. 静态看板和演示数据不计入正式能力。
4. 通用三步检查不能自动等同于法规检查、不符合项和事故整改。
5. 规格中规划但代码未兑现的功能不计为已实现。

## 4. 整体能力对比

| 维度 | 参考平台 | 苏南平台现状 | 判断 |
|---|---|---|---|
| 产品定位 | 航运公司安全管理体系平台 | 企业综合工作与船舶业务平台 | 定位差异 |
| 运行终端 | PC 管理端加微信小程序 | 企业微信 H5，兼容桌面与移动 | 定位差异 |
| 统一认证 | 平台账号、组织权限 | 企业微信 OAuth、岗位角色 | 苏南有优势 |
| 原生审批 | 以平台自建流程为主 | 企业微信原生审批桥接和状态镜像 | 苏南有优势 |
| 专业安全主数据 | 船舶、船员、岸基、设备、检查项等较完整 | 企业、证照、船舶基础实体已有，人员和设备专业档案不足 | 部分实现 |
| 通用流程 | 多角色、多人并行、回退、终止、作废、抄送 | 通用状态机和步骤动作，企业微信审批 | 部分实现 |
| 跨模块自动化 | 多处自动生成、前置校验和任务转移 | 培训完成触发审批等少量联动 | 部分实现 |
| 现场证据 | 小程序拍照、签名、定位、消息直达 | 有 JS-SDK 基础，未在全业务统一落地 | 部分实现 |
| 报表归档 | 多域 Excel、PDF、水印、统计 | 采购较完整，工作平台打印和导出不完整 | 部分实现 |
| 监管协同 | 海事平台方案、问题、处罚等交换 | 办事外链和海事检查记录为主 | 缺失 |

## 5. 逐域功能矩阵

| 参考能力 | 苏南现状 | 状态 | 主要缺口 | 建议 |

| 汇总与报告 | 通用会议/打印可局部承载 | 缺失 | 无船舶报告、公司总报告和分发 | 建设报告生成器 |
| 内审不符合 | 通用检查整改 | 部分实现 | 无内审来源和自动转不符合 | 接入统一 CAPA |

### 5.10 监控、海事和信息服务

| 参考能力 | 苏南现状 | 状态 | 主要缺口 | 建议 |
|---|---|---|---|---|
| AIS/CCTV 入口 | 船舶监控外部链接 | 部分实现 | 无内置台账、异常记录和权限审计 | 先做单点登录和事件回写 |
| 值班打卡交接 | 值守、考勤模块 | 部分实现 | 无真实定位、班次交接和未结事项 | 建设值班交接 |
| 海事安全检查 | 海事安检模块 | 部分实现 | 主要是内部记录 | 增加监管问题结构和回执 |
| 监管方案和消息接收 | 无数据接口 | 缺失 | 无监管平台同步 | 建设适配器和消息队列 |
| 外审问题转整改 | 无自动转单 | 缺失 | 外部问题不能进入内部 CAPA | 接入问题中心 |
| 安全信息发布 | 办事、会议、制度可局部承载 | 部分实现 | 无分类订阅、确认和阅读统计 | 建设安全信息中心 |

### 5.11 统计、消息和平台治理

| 参考能力 | 苏南现状 | 状态 | 主要缺口 | 建议 |
|---|---|---|---|---|
| 多域统计导出 | 采购和考勤有相关入口 | 部分实现 | 工作平台导出任务未完整产出文件 | 建设统一报表任务 |
| PDF 归档 | 采购 PDF 完整，工作平台快照可生成 | 部分实现 | 工作平台缺直接下载，缺水印和版本标识 | 统一文档服务 |
| 消息中心 | 企业微信审批通知、证书提醒 | 部分实现 | 无覆盖所有业务的统一消息中心 | 建设站内消息加企业微信通知 |
| 统一待办 | 审批中心和各模块列表分散 | 缺失 | 无任务聚合、逾期和深链 | 建设统一任务中心 |
| 任务日历 | 工作平台有静态排程展示 | 缺失 | 不是实际任务数据 | 建设计划任务日历 |
| 抄送 | 企业微信审批可提供部分能力 | 部分实现 | 系统记录没有统一抄送轨迹 | 建设业务抄送实体 |
| 作废与审计 | 部分模块有状态和审计 | 部分实现 | 无统一作废申请、审批和恢复策略 | 增加作废流程 |
| 组织权限 | 企业微信组织和七类角色 | 部分实现 | 船舶、本人与步骤动作权限不足 | 建设 ABAC 数据权限 |

## 6. 关键业务链路差距

### 6.1 检查到不符合项闭环

参考链路：

`检查计划 -> 检查任务 -> 多人检查 -> 问题判级 -> 自动生成不符合项 -> 原因分析 -> 纠正措施 -> 完成证据 -> 验证 -> 有效性评价 -> 关闭`

苏南现状：

`新建记录 -> 现场检查 -> 标记整改 -> 整改执行 -> 审核关闭`

缺少：

- 检查项库和法规来源
- 检查计划与任务分派
- 多人并行检查与全部完成门槛
- 问题分级、重大隐患升级
- 独立不符合项实体
- 根因分析和纠正预防措施
- 逾期提醒、升级和有效性验证
- 与内审、事故、海事问题的统一来源关联

升级建议：

1. 新建 `inspection_plan`、`inspection_task`、`inspection_item_result`。
2. 新建统一 `issue`，来源可为检查、内审、事故、设备和监管平台。
3. 新建 `capa_action` 和 `verification`。
4. 用事件规则自动转单和发送企业微信待办。
5. 关闭前强制检查证据、验证人和验证结论。

[图片内容：目标闭环流程图，从检查计划到 CAPA 关闭，突出“自动生成不符合项”和“验证关闭”两个节点。]

### 6.2 年度计划到执行评价

参考链路：

`年度计划 -> 审批 -> 自动生成月度/单次任务 -> 执行 -> 评价 -> 改进项`

苏南现状：

年度计划、培训、演练、维护等模块相互独立，主要靠人工重复创建记录。

升级建议：

- 建设统一计划项模型，允许关联培训、演练、维护、检查和内审。
- 计划批准后自动生成任务。
- 支持改期、取消、补做和变更审批。
- 看板基于真实任务计算完成率和逾期率。
- 评价发现问题时自动进入问题中心。

### 6.3 人员调配、交接与开航前置条件

参考链路：

`人员调配 -> 资格/健康/证书校验 -> 熟悉职责 -> 工作交接 -> 待办转移 -> 船长确认 -> 允许上岗或开航`

苏南现状：

企业微信组织可确认人员身份，培训模块可记录进度，但没有船员任职、交接和门禁规则。

升级建议：

- 建立船员与船舶任职关系。
- 证书、健康、培训和熟悉职责形成资格校验。
- 离船交接时转移未完成任务和问题。
- 航次审批发起前自动校验最低配员、证书和熟悉状态。

### 6.4 设备计划、缺陷、修理与备件

参考链路：

`设备模板 -> 年度计划 -> 月度任务 -> 执行确认 -> 缺陷 -> 修理/采购/备件 -> 验收 -> 统计`

苏南现状：

有设备维护、设备检验、采购和后勤资产模块，但没有共享设备主数据和业务关联。

升级建议：

- 统一设备编码和船舶设备树。
- 维护周期自动生成计划。
- 执行发现缺陷后自动创建缺陷单。
- 缺陷单可发起修理、采购或备件领用。
- 采购到货和备件入库回写缺陷处理。
- 验收通过后关闭缺陷并计算设备可靠性指标。

### 6.5 内审与管理评审

参考链路：

`内审计划 -> 审核组 -> 首次会议 -> 审核方案 -> 个人记录 -> 汇总 -> 不符合项 -> 末次会议 -> 船舶报告 -> 公司总报告 -> 分发`

苏南现状：

年度计划、会议和检查模板能保存局部信息，但没有统一内审对象和报告链。

升级建议：

- 内审作为专用聚合流程，不用单个通用表单代替。
- 首次和末次会议复用会议能力，但增加签到、签名和内审关联。
- 审核发现自动进入统一问题中心。
- 报告从结构化审核结果自动生成，并支持水印分发。

### 6.6 移动现场证据与待办

参考平台：

- 任务日历
- 通知与确认
- 待办深链
- 现场照片
- 手写签名
- 定位打卡
- “我发起的”

苏南现状：

- 企业微信深链和审批跳转基础较好
- 文件、JS-SDK 和身份基础已存在
- 业务页没有统一任务日历、上传、签名、定位和“我发起的”

等效升级方案：

- 不必新建微信小程序，优先在企业微信 H5 建设统一移动任务中心。
- 用企业微信 JS-SDK 提供拍照、定位和扫一扫。
- 使用 H5 签名板并将签名哈希、时间、用户和业务记录绑定。
- 任务消息通过企业微信应用消息深链到具体步骤。
- 关键现场表单支持本地草稿和断网恢复。

## 8. 目标架构建议

### 8.1 安全领域核心

建议增加以下领域服务：

| 领域服务 | 核心对象 |
|---|---|
| 主数据中心 | 企业、组织、船舶、人员、任职、设备、证书、字典 |
| 计划任务中心 | 年度计划、计划项、执行任务、日历、改期、取消 |
| 检查中心 | 检查模板、检查项、检查计划、任务、结果 |
| 问题与 CAPA 中心 | 隐患、不符合、事故问题、原因、措施、验证 |
| 人员安全中心 | 调配、交接、熟悉职责、培训、考试、健康和资格 |
| 船舶作业中心 | 作业许可、航次、燃油、高风险作业和防台 |
| 应急中心 | 计划、演习、训练、评价和应急事件 |
| 设备维修中心 | 设备树、周期计划、缺陷、修理、备件和库存 |
| 文件与内审中心 | 受控文件、变更、分发、内审、报告 |
| 消息任务中心 | 待办、通知、抄送、升级、企业微信消息 |
| 报表中心 | 异步导出、PDF、水印、统计口径和审计 |
| 集成中心 | 企业微信、AIS/CCTV、海事监管和外部业务系统 |

### 8.2 流程底座需要增强的能力

当前通用状态机建议增加：

- 步骤执行角色与具体执行人
- 多人并行及“全部完成/任一完成/按比例完成”
- 条件分支和前置校验
- 退回到指定步骤
- 撤回、终止、作废和重开
- 抄送和阅读确认
- 逾期、催办和升级
- 跨模块自动创建、更新和关闭
- 任务转移和代理
- 电子签名、定位和证据要求
- 完整动作审计

### 8.3 数据权限需要增强的能力

建议从单纯角色权限升级为角色加属性权限：

`是否可操作 = 角色权限 + 所属部门 + 所属船舶 + 是否本人记录 + 是否任务参与人 + 记录状态`

最低要求：

- 船员默认只能查看本人、本船或本人参与任务。
- 整改责任人只能提交本人措施。
- 复核人不能由整改责任人兼任，除非规则明确允许。
- 管理员查看敏感数据应留下审计记录。
- 外部链接、附件和导出必须继承记录权限。

## 9. 分阶段升级路线

周期是产品与研发排期建议，实际应根据团队规模和监管要求调整。

### 9.1 P0：可信运行基础，建议 0 至 2 个月

目标：先解决当前通用平台的可用性和可信性问题。

| 工作项 | 交付结果 |
|---|---|
| 修复工作平台数据范围 | 船员按本人、本船、参与任务隔离 |
| 增加动作权限 | 每个步骤明确执行人和复核人 |
| 统一附件上传 | 所有工作平台模块支持选文件、拍照、预览和删除 |
| 完成打印下载 | 工作平台 PDF 可预览、下载并带版本信息 |
| 完成导出任务 | 考勤和工作平台导出真正生成文件 |
| 清理演示数据 | 看板全部来自真实接口或明确标识演示 |
| 修复台账提交链路 | 草稿、提交、审批、完成状态在前端可操作 |
| 建设统一待办最小版 | 聚合本人待处理步骤和企业微信审批 |
| 补齐审计 | 记录查看、导出、状态动作和管理员操作 |

P0 验收标准：

- 不同船舶船员互不可见非授权记录。
- 非当前执行人不能推进步骤。
- 任意工作平台记录可上传附件并下载归档 PDF。
- 所有看板数字可追溯到真实记录。

### 9.2 P1：检查、隐患与 CAPA，建议 2 至 4 个月

目标：建立参考平台最关键的安全闭环。

| 工作项 | 交付结果 |
|---|---|
| 检查项库 | 法规、公司和船舶自定义检查项 |
| 检查计划与任务 | 周期、船舶、人员和多人检查 |
| 统一问题中心 | 隐患、不符合和外部问题统一来源 |
| CAPA | 原因、措施、责任人、期限和验证 |
| 自动转单 | 检查发现按规则生成不符合项 |
| 逾期升级 | 企业微信提醒、催办和升级 |
| 重大隐患 | 分级确认和上报材料 |
| 统计 | 发现率、整改率、逾期率和重复问题 |

### 9.3 P2：计划、人员、作业与应急，建议 4 至 7 个月

目标：把已有同名模块从单次记录升级为可执行链路。

重点交付：

- 年度计划自动生成培训、演练、检查和维护任务
- 船员档案、任职、证书、健康、调配和交接
- 熟悉职责和开航前置校验
- 培训需求、计划、签到、考试和评价
- 航次审批安全校验
- 有限空间、明火、危险货物、高空舷外等专用许可
- 燃油审批后自动生成供受油检查
- 应急计划、实施、评价和改进项
- 移动拍照、签名、定位和断网草稿

### 9.4 P3：设备、备件、文件与内审，建议 7 至 10 个月

重点交付：

- 船舶设备树和维护周期
- 年度、月度维护计划
- 设备缺陷、修理、厂修和验收
- 备件申领、发放、使用、库存和盘点
- 受控文件变更、分发、回执和水印
- 完整内审与管理评审
- 自动生成船舶报告和公司总报告

### 9.5 P4：监管协同与经营分析，建议 10 至 12 个月

重点交付：

- 海事监管平台消息、方案、问题和回执适配
- AIS/CCTV 事件回写和监控台账
- 全域指标中心和监管报表
- 风险趋势、重复问题和设备可靠性分析
- 多公司、多船舶产品化配置

## 10. 优先级建议

| 优先级 | 功能 | 原因 |
|---|---|---|
| P0 | 数据范围和动作权限 | 直接影响数据安全和流程可信性 |
| P0 | 通用附件、打印、导出 | 决定现场证据和归档是否可用 |
| P0 | 真实待办和状态链 | 解决用户找不到任务和台账无法提交 |
| P1 | 检查项、问题和 CAPA | 是安全管理闭环的核心 |
| P1 | 计划任务化 | 减少人工重复建单和漏项 |
| P1 | 多人签认和逾期升级 | 对船舶检查、作业和内审都通用 |
| P2 | 船员任职和资格校验 | 支撑开航和人员管理 |
| P2 | 高风险作业许可 | 直接关系现场安全 |
| P2 | 移动证据链 | 提升现场真实性和可追溯性 |
| P3 | 设备与备件闭环 | 提升设备可靠性和成本可控性 |
| P3 | 文件和内审 | 支撑体系审核和持续改进 |
| P4 | 监管数据交换 | 依赖外部接口和合规协商 |

## 11. 关键验收标准

达到“能够实现参考平台主要功能”的最低验收条件如下：

1. 每个安全计划能自动生成可执行任务，并可统计完成、逾期、改期和取消。
2. 每个检查问题都有来源、级别、责任人、期限、证据、复核人和关闭记录。
3. 检查、内审、事故和监管问题都能自动进入同一不符合与 CAPA 闭环。
4. 船员只能访问本人、本船或本人参与的任务，步骤只能由授权人员执行。
5. 多人检查和多人培训支持全部完成门槛，并保存每人的签认时间。
6. 航次审批能校验证书、人员、培训熟悉和未关闭重大问题。
7. 高风险作业具备许可、检查、检测、监护、现场照片和签名证据。
8. 设备维护能从计划追踪到任务、缺陷、修理、备件和验收。
9. 文件变更、内审和管理评审可生成受控 PDF、分发回执和完整审计轨迹。
10. 用户可在企业微信统一待办和任务日历中直接进入本人下一步操作。
11. 所有导出、PDF、附件和外部链接遵循记录数据权限。
12. 监管数据接口失败时可重试、对账并保留人工补录路径。

## 12. 不建议的做法

- 不建议为每个参考模块复制一套几乎相同的页面和表。
- 不建议继续只增加模块名称而不增加专用规则。
- 不建议让船员手工输入船舶 ID、人员 ID 或文件 ID。
- 不建议用摘要文本代替结构化检查项、责任人和验证记录。
- 不建议把首页静态卡片作为管理统计。
- 不建议先做复杂大屏，再补数据权限、证据和闭环。
- 不建议为了形式对齐单独建设微信小程序，企业微信 H5 能满足时应优先复用现有入口。

## 13. 推荐产品决策

### 13.1 继续保留企业微信 H5

企业微信是苏南当前产品的重要优势。通过 H5、JS-SDK、应用消息和原生审批，可以实现参考平台小程序的大部分移动能力，并减少双端维护。

只有在以下情况同时成立时再评估独立小程序：

- 外部船员或合作方不在企业微信组织中
- 需要微信公众生态触达
- 企业微信 JS-SDK 无法满足关键设备能力
- 有独立运营和发布团队

### 13.2 建设统一安全问题中心

这是最优先的领域能力。隐患、自查、检验、海事安检、内审、设备缺陷和事故发现的问题，应进入统一问题模型，再按类型和级别走不同流程。

### 13.3 用计划任务中心连接现有模块

不必推翻培训、演练、维护和检查模块。先增加计划任务中心，让年度计划能自动创建这些模块的执行记录，并把状态回写计划。

### 13.4 采购作为维修和安全费用的下游

安全费用、设备修理和备件申请不应重新建设一套审批。专业模块创建采购需求后，调用现有采购流程，并把审批、到货和金额回写来源业务。

## 14. 实施依赖与风险

| 风险 | 影响 | 控制建议 |
|---|---|---|
| 安全业务规则未统一 | 不同部门要求冲突 | 先确定术语、状态和责任矩阵 |
| 组织岗位数据不准确 | 权限和任务分派错误 | 建立企业微信组织同步和例外维护 |
| 船舶与人员主数据质量低 | 校验、统计和监管上报失真 | 先治理主数据再做自动化门禁 |
| 外部监管接口不稳定 | 消息丢失或状态不一致 | 使用幂等、重试、对账和人工补录 |
| 现场网络不稳定 | 图片和表单提交失败 | 增加压缩、续传和本地草稿 |
| 通用引擎过度复杂 | 研发周期失控 | 通用能力与专用聚合流程分层建设 |
| 历史数据迁移困难 | 新旧统计不一致 | 设迁移批次、来源标识和只读历史区 |
