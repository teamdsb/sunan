# 原始目标与主要业务链路核查

## 结论

四大板块已有真实页面、接口和数据库实现，办事入口、企业资料与证照、采购申报审批等主要能力已有自动化证据。**尚未完整兑现原始目标**：工作平台考勤导出缺少业务数据，培训、签到和燃油统计等仍有手工台账代替业务闭环的情况。最初核查发现的船舶自查跳步、无证据关闭问题已在后续选定 MVP 补充中修复，其他业务入口不能据此视为已完成。

最初核查完成原件读取、源码对照、现有测试验证及两项真实数据库缺陷复现。下面的问题清单保留核查时的证据；后续修复情况见本文末尾“选定 MVP 链路实施补充”。M9 未启动。不能将其他安全管理模块的存在视为原始工作平台链路已经闭合。

## 优先处理的实质缺口

### 1. 整改可以无证据关闭，步骤可跳序

原件船舶自查和海事安检明确要求整改前后照片形成闭环。对当前代码运行独立 PostgreSQL Testcontainers 复现，使用普通船务角色作为记录创建人：

1. `POST /api/v1/workbench/records` 新建 `shipping_self_inspection`，提供船名、范围、问题、期限；不上传附件。
2. 向 `POST /api/v1/workbench/records/:id/actions` 发送 `{"actionType":"submit_review"}`，返回 201。
3. 再发 `{"actionType":"close_record"}`，返回 201；详情状态为 `closed`，三步骤全部仍为 `pending`，`attachments=[]`。
4. 另新建一条记录，直接发送 `{"actionType":"complete_step","payload":{"stepCode":"review_close"}}`，同样返回 201，跳过现场检查和整改。

两项临时回归分别要求拒绝上述动作（409），均失败，实际响应为 201。缺陷对应 `apps/api/src/modules/workbench/workbench.service.ts:2021` 的动作执行和 `:3837` 的状态检查；关闭前未验证步骤、整改证据、独立审核条件。临时测试文件已移除，本节保留重现步骤。

### 2. 考勤导出只有元信息，未导出考勤

原件 `考勤表 -模版.xlsx` 包含姓名、部门、逐日记录和确认签字。实际调用构建后的 `buildAttendanceWorkbook('2026-02', 'finance_dept')`，解析生成的 XLSX，仅有：

```text
month | departmentCode | generatedAt
2026-02 | finance_dept | <生成时间>
```

`workbench.service.ts:1740` 的 PDF 分支同样只输出月份、部门、生成时间；`:1793` 的 Excel 构造没有查询或传入考勤记录。导出任务能成功、文件格式正确，不代表报表内容满足要求。

### 3. 定位与时段统计并未完整实现

`workbench.service.ts:1273` 的 `locationInRange` 是文本字段；`:1647` 按用户填入的值统计。作业记录的 `isQinzhouRange`（`:3646`）仅按泊位/区域/船名文字包含 `qz` 或“钦州”推断。通用 EvidencePanel 虽可采集浏览器定位，但未与这里的考勤判定打通。

另外实际调用 `getHour('2026-09-07T13:00:00+08:00')` 得到 `5`，因此作业记录会被计入上午；该分支使用 UTC 小时，未按业务时区统计。

### 4. 培训、会议、油耗的关键结果依赖手填

- 培训：前端 `WorkbenchHomePage.tsx:820` 提交手填进度，后端 `workbench.service.ts:4089` 将“状态完成 / 有完成时间 / 进度至少 100%”任一满足视为完成；未验证各参训人实际学习。
- 会议：`workbench.service.ts:709` 保存签到人数和群链接，未发现建群/视频会议会话或逐人签到模型。
- 燃油：`:1357` 要求用户填月耗和剩余量；`:1450` 的车辆表单无加油量/月耗字段。已有字段和审批无法替代月度计算与提醒。

### 5. 工作平台打印为通用数据快照

`workbench.service.ts:2316` 把标题、摘要、payload JSON、步骤文字、附件文件名与 ID 生成 PDF，标题为 `Workbench Print Snapshot`；没有把作业票、密闭空间申请、检查单的原表布局及照片本身绘入打印文件。A4/A3 尺寸支持已实现，业务表格内容和版式仍需对照原件补齐。

### 6. 使用授权与任务下发语义仍需对齐

原始“注册-审批-才能使用”被整理文档弱化为“审批人具备权限”。本轮已在 `docs/需求文档.md` 恢复原始表述并登记差异。当前 OAuth 通讯录授权是否可以被业务接受为替代方案，尚无本轮确认依据。

通用工作平台记录创建时 owner/applicant 为创建者，assignee/reviewer 初始为空；存在参与人分配 API，但这不能证明培训、叫应、演练各入口已具备原件要求的下发、执行、逐人反馈和督促闭环。安全任务中心有另外的实现与测试，仍需逐入口建立业务关联。
