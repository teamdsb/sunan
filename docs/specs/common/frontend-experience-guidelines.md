# 前端体验与企业微信 H5 指引

> 状态：当前跨领域体验规格。用于约束页面视觉、交互、企业微信工作台直达、移动端适配和首屏性能，不替代各领域 UI 页面规格。

## 适用范围

- 适用于 `apps/web/src` 下所有面向用户的 H5 页面、模块首页、抽屉导航、列表、详情、表单、审批、文件、通知和错误态。
- 适用于跨模块设计决策：当一个能力可以放在 H5 内、企业微信工作台、企业微信消息、JS-SDK 或后端集成时，必须先按本指引判断运行边界。
- 各领域 `docs/specs/<domain>/ui/` 仍负责具体字段、流程和权限；本文件负责体验基线和验收门槛。

## 企业微信运行上下文

- 企业微信是主运行容器，不是附属登录入口。设计产品、接口、状态和错误恢复时，应默认用户从企业微信工作台或企业微信消息进入。
- 工作台应用入口应视为独立深链。不要假设用户先进入 `/my`，也不要要求用户经过宽泛的站内导航才能到达业务任务。
- 内部导航只作为补充能力。核心流程应支持短任务会话：打开入口、完成当前任务、必要时回到企业微信或等待消息通知。
- 认证恢复、权限不足、网络异常、文件预览、上传、审批跳转和重新认证入口都要适配企业微信 H5 环境。
- 涉及企业微信能力时，先检查 `docs/specs/wecom/README.md` 及对应 OAuth2、JS-SDK、消息、审批桥规格。

## 视觉基线

当前标杆为 `/my` 我的模块首页和移动端模块导航抽屉。后续页面应延续同一套蓝白企业 H5 语言，而不是回到旧的绿色/纸面风格。

- 主色使用深蓝标题、企业蓝操作色和少量青蓝强调：例如 `#102a43`、`#1769e0`、`#0b58c7`、`#19a7ce`。
- 背景以白色、浅蓝、雾面渐变和低透明边框构成，避免大面积高饱和色块。
- 页面卡片使用清晰层级：浅边框、轻阴影、8-18px 圆角；不要把页面区块层层包成卡片。
- 图标使用线性风格，和按钮、入口、状态保持一致。可使用 Ant Design icon，但不要让图标成为首屏体积失控的原因。
- 字体以移动端可读为先：中文标题加粗，正文保持紧凑；不要用超大营销式 hero 排版承载业务工具页面。
- 页面必须能在常见企业微信手机视口下完整扫描，避免文本溢出、按钮挤压、横向滚动和浮层遮挡关键操作。

### 苏南船舶 OA 控制台风格

2026-06 UI 统一改造后，桌面端主入口参考 `new-ui-photo/sunan-oa-desktop-*.png` 的控制台语言，移动端参考 `new-ui-photo/sunan-oa-mobile-responsive.png` 的单列 H5 语言。

- 顶部品牌区保持“苏南船舶管理 / 企业微信 H5 工作台”一致表达，桌面端使用白色顶栏、蓝色胶囊导航、成员身份与重新认证入口；移动端使用品牌标题、模块分段导航和底部模块导航。
- 模块首页优先组织为业务看板：主标题说明当前任务域，首屏给出主操作；核心区按“指标 / 入口 / 清单 / 待办 / 预警”组合，而不是散落的单张卡片。
- `/my` 首页必须保留船舶视觉资产，并将其作为业务识别和状态概览的一部分；不得替换为无关插画或纯装饰背景。
- 卡片圆角控制在 8-10px，边框使用浅蓝线，阴影轻量；禁止嵌套大卡片包小卡片造成层级混乱。
- 表格、筛选和入口卡在桌面端以横向扫描为主；移动端全部降为单列或两列入口，不出现横向页面滚动。表格无法压缩时，表格自身可横向滚动。
- 操作色使用企业蓝，状态色仅用于风险和进度：红色紧急、琥珀审批/中风险、青绿完成/正常。不要把大面积背景改成高饱和色块。
- 页面可加入静态运营提示和示例排程，但不得写死截图中的具体人员姓名；真实用户信息应来自认证状态或使用通用成员文案。

## 交互模式

- 模块首页负责快速进入当前业务域，不负责预加载全站功能。入口文案应清楚说明当前模块可做什么。
- 移动端抽屉导航是辅助跨模块入口：需要显示当前模块高亮、用户身份、重新认证入口，并保持蓝白企业风格一致。
- 业务表单优先单列、分组清晰、主操作固定在用户自然完成路径附近；不要把桌面表格布局直接压缩到手机。
- 列表页优先支持筛选、搜索、状态查看和详情进入；复杂筛选应可折叠，避免首屏被表单占满。
- 详情页优先呈现业务状态、关键字段、附件和可执行动作；审批、打印、导出等高影响动作要有明确反馈。
- 加载态、空态、错误态和权限不足态应是业务可理解的，不使用开发术语。企业微信内可恢复的问题应提供重新认证或返回入口。

## 首屏性能与分包

- 入口路由必须按用户实际打开的企业微信工作台应用加载。进入 `/my` 不应加载办事、采购、工作平台等无关业务页；进入其他业务入口也不应为 `/my` 付费。
- 业务页面、模块壳层和高成本 UI 依赖优先使用 route-level lazy loading。共享 vendor chunk 只放稳定基础依赖，避免把全量 Ant Design 或无关业务包变成首屏 `modulepreload`。
- 生产构建后检查 `dist/index.html`：首屏 `modulepreload` 应只包含当前入口确实需要的基础 chunk，不应出现无关业务页面 chunk。
- `pnpm --filter web build` 不应出现 circular chunk 警告或超过 500 kB 的业务 chunk 警告。若确实无法避免，必须在变更说明中记录原因和后续拆分点。
- 首屏图片优先使用 WebP/AVIF，控制真实展示尺寸和压缩体积。模块 hero 图应服务业务识别，不作为纯装饰背景堆叠。
- 不为“可能会点”预加载大页面。只有经过测量且能改善当前企业微信入口任务时，才允许增加针对性预取。

## 资产与实现

- 业务视觉资产可以使用生成图，但必须落成受控静态资源，压缩后再进入仓库。
- 大背景图需要和文本遮罩、移动端裁切、不同视口比例一起验证，不能只按单一 iPhone Pro Max 比例设计。
- CSS 改造优先沿用现有组件边界和 class，不为了视觉调整引入无关状态或业务逻辑。
- 可复用视觉模式应沉淀为 class 或组件约定；一次性页面特效不要污染其他模块。
- 任何新的第三方前端依赖都必须说明体积、分包影响和替代方案。

## 验收清单

后续每个前端页面改造完成前，至少检查：

- 企业微信直达：直接打开目标 URL 能完成认证恢复、状态初始化和页面渲染。
- 视觉一致：蓝白企业风格、标题层级、卡片、图标、按钮、抽屉或导航状态和 `/my` 标杆一致。
- 移动适配：320px 到常见企业微信手机宽度无横向滚动，文本和按钮不重叠。
- 交互完整：加载、空态、错误、权限不足、重新认证、返回或跳转路径都有明确反馈。
- 性能守门：无无关业务页首屏预加载；构建无 circular chunk 和大 chunk 回退。
- 资源体积：图片、图标和新增 CSS/JS 有明确必要性，压缩后体积可接受。
- 测试通过：至少运行受影响页面测试、路由测试和 `pnpm --filter web build`。

## 变更入口

- 更新通用体验规则时，同时更新 `docs/specs/common/README.md` 和 `docs/inventory.md`。
- 改动领域页面时，在对应 `docs/specs/<domain>/ui/*.md` 中补充页面特有规则，并引用本文件作为体验基线。
- 企业微信能力变化时，同步检查 `docs/specs/wecom/` 下的规格，避免 H5 页面假设和企业微信能力边界冲突。
