# M9 执行计划：平台管理与配置升级

> 状态：已重新规划，功能实施未开始。原专业安全 M9 已按用户要求删除，本计划使用同一编号重新立项；本轮规划不代表实现或上线。

需求与关键规则以 [M9 需求](../requirements/M9-平台管理与配置升级.md) 为准；任务拆分见 [backlog](M9-wave-backlog.md)，执行入口见 [提示词索引](../prompts/README.md)。

## 1. 不可改变的边界

- 全部用户包含从未登录的通讯录成员；受主应用可见范围限制时公开说明覆盖情况，不能把局部成功当成全企业同步。
- 企业微信身份资料与平台部门/业务角色覆盖分开；人工设置不被 OAuth、刷新或同步覆盖。
- 系统管理员唯一来源为 env；主应用企业 ID、AgentID、Secret、认证与事件回调、签名、域名等继续 env。
- 本期后台只开放同企业可选通知应用。无覆盖用主应用，半配置拒绝，错误覆盖不静默回退。
- 角色能力和各模块角色/部门/参与关系组合沿用现有规则；有效部门用于已有部门判断，船舶关系、任务参与人等继续独立约束。列明角色授予的跨部门能力，不因新增管理页开放全员业务数据。
- 不恢复原专业安全扩展，不硬删除用户，不通过后台写企业微信组织架构，不实施生产发布。

## 3. Wave 1：身份与配置基线

### 工作

1. 再核对 OAuth、JWT 请求/刷新、角色解析、env 管理员和各业务部门/收件人旁路，建立受影响入口清单。
2. 冻结来源快照、人工部门/角色独立模式、账号状态、生效算法、版本冲突、来源乱序和前端刷新契约。
3. 冻结通讯录同步批次、可见范围/完整性提示、幂等身份、失败处理及未知历史登录状态。
4. 冻结配置白名单、完整主应用缺省、独立通知应用、加密密钥、版本、缓存、测试与重试规则。
5. 确认现有实体/外键和历史数据质量，设计增量迁移、权限对照与兼容回滚，补充必要 API/DB 决策；明确接口错误码及管理写入白名单；权限矩阵包含“人工财务部门 + shipping 角色”、总经办跨部门、空部门、空业务角色、船员和任务参与人组合。

### 交付与退出条件

- 在现有 common/auth、notification、wecom 等契约中明确实施状态与目标变更；只补必要的新契约，不将未来规则写成已实现行为。
- 输出接口、字段和来源权限矩阵；管理 API 均以 `system_admin` 为门禁，正常业务的 `/auth/me` 不需要管理员权限。
- 核心验收 U1-U9、C1-C4、R1 均有对应验证方式；未知权限/可见范围不通过猜测确定。
- 回滚不会忽略人工撤权/停用或通知覆盖；明确所有实例重载管理员 env 的发布步骤，以及既有 disabled 与 env 提升/撤销的组合行为。

## 4. Wave 2：全部用户与授权后端

### 工作

1. 完成用户/部门来源、覆盖、独立授权版本、同步批次及审计的增量 migration，保留用户 UUID 和业务关联；登录角色基线兼容，现有业务旁路权限差异形成收敛清单并核对影响。
2. 实现统一有效授权服务，接入 OAuth、me、JWT 请求和刷新；使用局部更新、事务与并发控制防止重登/同步覆盖人工设置。
3. 实现全目录读取和管理员手动同步，处理多部门、分页、重复用户、部分失败与可见范围收缩，禁止按名单缺失推定离职。
4. 实现管理员分页列表、详情、查询筛选、部门/角色编辑、恢复跟随、平台停用/恢复和变更历史；env 管理员资格只读且不可被后台停用。

### 验证与退出条件

- 真实 PostgreSQL 覆盖重复同步、OAuth 与管理员并发、两个管理员 409 冲突、来源乱序及外键不变。
- 人工空角色不回填，停用不能被 OAuth 或 token 刷新绕过；所有认证返回最新有效用户。
- 旧 token 下一受保护请求使用新权限；非管理员和伪造字段请求被拒绝。
- 目录范围/失败/未知历史登录均可查询，新增未登录成员不伪造登录事实。

## 5. Wave 3：管理后台与业务权限收口

### 工作

1. 在现有系统设置中添加用户管理页面；实现搜索、筛选、分页、来源/生效对照、逐人编辑、变更原因、有效结果预览、历史、同步进度和错误反馈。
2. 完成身份刷新与业务查询缓存失效，处理本人权限变更、页面恢复、聚焦、权限类 403 和停用会话；移动端能完成主要管理流程。
3. 统一采购审批/收件人、自查候选人、证书提醒范围、企业信息/制度范围、任务和学习成员选择等读取身份的位置，移除独立角色推导及历史管理员快照授权。
4. 回归部门与角色不一致、多部门、船员/船舶、参与人和历史快照，确保部门修改不会静默转移任务或改写历史归属；特别核对 crew 在提醒旁路被额外补 shipping 的旧行为。

### 验证与退出条件

- 浏览器完成“同步未登录成员 → 人工部门与角色 → 重新授权 → 旧会话验证 → 恢复跟随”流程。
- U5/U7/U9 有真实业务行为验证；不能仅证明菜单隐藏。
- 所有业务候选人、可见范围与后台展示使用统一有效身份；完整性未验证/部分失败有明确提示。
- 变更成功、冲突、无权限和网络失败可恢复，不残留旧身份业务缓存或无限刷新。

## 6. Wave 4：推送设置与统一发送

### 工作

1. 增加配置持久化、认证加密、独立 env 密钥、乐观锁与脱敏审计；无配置时不复制主应用 Secret 入库。
2. 实现通知应用解析及按企业/应用/配置版本隔离的 token、锁与缓存，保持 OAuth/通讯录/SDK/回调等使用主应用。
3. 系统设置提供主应用状态只读、可选 AgentID/Secret、保留已存 Secret、验证连接、定向测试发送、保存与明确清除覆盖。
4. 证书提醒、采购与计划任务全部接入；统一有效收件人，保存必要投递结果与配置来源，保留业务去重和失败重试历史。

### 验证与退出条件

- C1-C4 全覆盖：默认、完整覆盖、半配置、空白保留、清除、读取/解密错误、多实例、轮换、缓存隔离和成功不重发。
- 数据库密文、API、请求日志、错误与审计无明文 Secret；配置缺失与配置读取失败能够区分。
- 测试连接不冒充实际送达；草稿测试不影响已保存配置，消息仅发明确测试对象。
- 配置失败和发送结果不确定可查，后者有人工核对/处理入口，不自动跨应用重试；发送前按当前有效身份排除不可用/无资格成员。

## 7. Wave 5：迁移回归与验收

### 工作

1. 使用脱敏/合成存量演练迁移前后授权对照、同步、覆盖、停用、配置默认和密钥恢复；不能把本地演练标成生产演练。
2. 在人工设置已存在的条件下验证兼容回滚，不允许直接运行忽略新授权或通知配置的旧代码；不能兼容时暂停 API 与相关推送入口/worker；配置恢复创建递增新版本，消息去重不受影响。
3. 完成必要自动化、浏览器及企业微信现场验收矩阵，归档测试数/失败数、范围限制、未执行项及遗留问题。
4. 更新实际已实现的操作手册、截图清单、env 示例说明、企业微信配置矩阵和迁移/发布/回滚操作步骤，不自动部署。

### 退出条件

- 需求验收表全部有证据；自动化检查通过，无未解决的越权、覆盖丢失、重复推送或明文凭据问题。
- 全目录验收先确认主应用覆盖全企业目标成员，部分/未验证不计全量通过；三端真机、真实全目录覆盖、真实独立应用收发逐项记录执行人、时间、结果；未执行项明确保留，上线前补齐必要现场项。
- 管理员能按说明完成用户调整、恢复跟随、排查同步范围及推送失败；说明哪些设置仍由 env 运维维护。
- 交付为可审查的实现与验收包，生产发布另行执行；没有生产操作证据不能声称上线。
