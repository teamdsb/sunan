# M9 Wave 3 管理后台与全业务权限整合设计

## 1. 背景与目标

M9-W2 已提供企业微信用户目录、来源同步、平台授权覆盖、授权版本和管理员 API，但当前前端只有个人设置页，业务模块仍存在从来源部门、职位或 `rawProfile` 旁路补角色的读取方式。本 Wave 交付 W3A-D：系统设置中的用户管理、当前身份刷新、权限失效处理，以及采购、提醒、证书对象、企业资料/制度、任务和学习选择器的有效身份收口。

本设计只修改当前仓库代码和必要契约，不写回企业微信组织、不开放 env 管理员配置、不实现消息推送配置（属于 W4），也不改变任务参与人、船舶关系或历史单据快照。

## 2. 方案选择

采用以 `AuthorizationService` 为唯一有效身份计算入口的适配方案：

- 管理页复用 W2 用户目录接口，补充同步后可选部门字典读取接口；前端只提交字段白名单、授权版本和原因。
- 业务模块在需要读取用户实体时调用 `AuthorizationService.getEffectiveAuthorization`，当前请求继续使用 `CurrentUser` 的已计算结果；删除从来源字段或 `rawProfile` 重新推导业务角色的旁路。
- 基础 API 查询层统一处理 403：先让当前用户查询失效并强制刷新；`/auth/me` 也不可用时清会话并只发起一次 OAuth，避免刷新循环。

相比只做页面，这能让界面显示和业务数据范围共享同一身份口径；相比重写所有角色判断，改动集中在已有旁路处，保留各模块既有的角色、部门和参与关系组合。

## 3. 后端设计

### 3.1 管理接口

保留 W2 既有路径和响应结构：

- `GET /api/v1/admin/wecom-users`：列表、搜索、筛选、分页、覆盖范围提示。
- `GET /api/v1/admin/wecom-users/:userId`：来源、平台、有效结果和最近审计。
- `GET /api/v1/admin/wecom-users/:userId/audits`：审计分页。
- `PATCH /api/v1/admin/wecom-users/:userId/authorization`：携带 `expectedAuthorizationVersion` 和非空 `reason`，仅允许部门模式、人工部门、角色模式、人工业务角色和平台状态。
- `POST /api/v1/admin/wecom-users/:userId/restore-departments`、`restore-roles`：分别恢复跟随和自动角色，不互相清除。
- `POST /api/v1/admin/wecom-directory-sync`、`GET .../:batchId`：手动同步和批次状态。
- 新增 `GET /api/v1/admin/wecom-departments`：返回已同步部门字典及最近同步覆盖提示，供人工部门选择和有效部门筛选使用。

所有接口继续由 JWT 和 `system_admin` 角色守卫保护。服务端拒绝管理员提权字段；管理员资格只从 env 读取。详情只返回脱敏来源字段，不返回完整 `rawProfile`。

### 3.2 有效身份适配

需要用户实体的业务服务注入 `AuthorizationService`。对每个用户实体：

1. 用 `getEffectiveAuthorization(user)` 检查企业、来源可用状态和平台状态。
2. 使用返回的有效部门和业务角色进行范围、候选人和收件人判断。
3. 人工角色为空时只保留 `all_authenticated`；人工部门模式不调用职位兼容推导。
4. 对明确保存的任务参与人、审批人和历史快照保留原值；只在新查询、新选择和发送前排除当前不可用或失去资格的成员。

重点收口位置：

- 证书提醒服务和提醒引擎：移除 `resolveRolesFromDepartments` 对当前用户/收件人的额外补角色。
- 证书对象、企业资料/制度：使用有效部门代码和有效角色，不读取来源部门覆盖。
- 自查候选人、学习人员选择器：以有效授权和可用状态过滤，不以 `rawProfile.status` 单独判断。
- 任务/学习选择器：继续保留参与关系和管理员边界，目录候选人改用有效身份服务。

### 3.3 身份失效契约

`/auth/me`、JWT 验证、token 刷新继续调用同一授权服务。平台停用、企业微信账号不可用或跨企业身份返回权限错误；系统管理员仍受企业微信不可用约束，但不受平台人工停用约束。

## 4. 前端设计

### 4.1 路由与页面

在 `/my/settings` 保留个人偏好，在 `/my/settings/users` 增加管理员可见的用户管理页。设置页只对 `currentUser.isAdmin` 显示入口，后端仍是最终门禁。

用户管理页由列表、详情抽屉和编辑弹窗组成：

- 列表列出姓名、UserID、来源部门、有效部门、有效角色、平台状态、登录状态、管理员来源和覆盖标记。
- 筛选包含姓名/UserID、部门、业务角色、平台状态、env 管理员、是否登录和是否人工覆盖；默认展示全部状态。
- 详情按“企微来源 / 平台设置 / 当前生效 / 历史”分组，明确“完整性未验证”和同步批次错误。
- 编辑先展示部门模式、部门多选、角色模式、角色多选、平台状态和原因；保存前显示有效部门、有效角色、可用状态的预览。
- 409 显示“数据已变化”，重新读取详情后保留用户当前输入；网络失败保留表单；停用和恢复显示影响提示。
- 同步按钮显示进行中、成功、部分成功、失败、读取数、新增数、更新数、失败数和覆盖口径；运行中重复点击显示现有批次。

页面在桌面使用表格和抽屉，在 H5 使用卡片列表、底部抽屉和分步编辑；加载、空态、错误、无权限和同步部分失败均有可操作反馈，页面不依赖菜单隐藏作为权限证明。

### 4.2 查询缓存和恢复

`baseApi` 新增用户目录相关标签。`AppShell` 不再因为已有 Redux 用户而永久跳过 `/auth/me`：在路由恢复、窗口聚焦和 `visibilitychange` 时强制刷新，并将结果写回 auth slice。用户管理保存本人后立即刷新当前身份并失效采购、提醒、证书、工作台和企业资料相关标签。

业务请求收到 403 时使 `CurrentUser` 失效并刷新一次；若当前身份接口也失败，清除 token、auth slice 和重定向目标后进入 OAuth。刷新动作带一次性锁，防止多个并行请求或失效身份形成无限循环。

## 5. 错误与并发处理

- 授权编辑使用授权版本乐观锁，冲突返回 409 和当前版本；前端重新读取详情，不覆盖未提交输入。
- 来源同步只更新来源字段，旧来源批次不会覆盖新来源；不因名单缺失停用成员。
- 部门选择只接受已同步字典中的 ID；人工部门找不到时保留设置并显示待核对。
- 403、停用、账号不可用、网络错误和同步部分失败分别显示，不能用空列表或 OAuth 重试掩盖权限错误。
- 业务发送和任务动作继续使用既有去重、参与人和快照逻辑；本 Wave 不引入消息配置或自动转移。

## 6. 验证设计

增加的自动化只覆盖行为风险：

- API：管理接口字段白名单、部门/角色人工空值、授权冲突、管理员停用限制、有效身份旁路收口、候选人排除不可用成员。
- Web：用户列表筛选/分页、详情对照、编辑预览与 409 恢复、同步状态、本人保存后的身份刷新、403 刷新和停用会话清理。
- 现有受影响模块测试继续运行，随后执行 API/Web lint、unit、integration、build 和 `git diff --check`。
- 新建 `docs/acceptance/M9-wave-3.md`，记录实际命令和结果。企业微信全目录覆盖、桌面/H5 真机、真实采购/提醒送达等现场证据在当前环境未执行时明确列为未执行，不标记为通过。

## 7. 非目标与风险

- 不开放系统管理员配置、主应用或 OAuth/env 参数写入。
- 不实现 W4 的独立通知应用、加密凭据和发送配置。
- 不改写历史单据快照，不自动改变船舶任职、任务参与人或审批归属。
- 现场企业微信可见范围若仍无法证明全量，管理页继续显示“完整性未验证”，全目录验收保持未完成。
