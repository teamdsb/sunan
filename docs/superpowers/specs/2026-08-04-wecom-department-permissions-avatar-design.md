# 企业微信部门权限与用户头像优化设计

## 背景

当前 OAuth2 登录已经从企业微信成员详情获取 `department`、`name`、`position` 和 `avatar`，但业务角色仍按部门中文名称推导。部门改名、同名或解析失败时可能造成权限漂移；原始部门 ID 也没有独立持久化，刷新令牌和 `/auth/me` 只能继续依赖已保存的名称。

前端已接收用户头像地址，但首页用户卡片、桌面端右上角、移动端顶部和移动抽屉仍显示固定图标或姓名首字。

## 目标

- 以企业微信返回的部门 ID 作为业务部门和业务角色的唯一判定依据。
- 系统管理员权限与部门彻底解耦。
- 保存原始部门 ID，使登录后各认证入口能稳定重算角色。
- 正确处理一名成员同时属于多个部门的权限并集和部门名称展示。
- 在全部用户身份展示位置优先显示企业微信头像，并提供可靠回退。

## 部门与角色映射

| 企业微信部门 ID | 部门名称 | 内部部门代码 | 业务角色 |
|---:|---|---|---|
| 1 | 公司成员（全体成员） | 无 | `all_authenticated` |
| 2 | 待设置部门 | 无 | `all_authenticated` |
| 3 | 总经办 | `general_office` | `general_office` |
| 4 | 财务部 | `finance_dept` | `finance` |
| 5 | 业务部 | `business_dept` | `business` |
| 6 | 船务部 | `shipping_dept` | `shipping` |
| 7 | 后勤部 | `logistics_dept` | `logistics` |
| 8 | 船员 | `shipping_dept` | `crew` |

部门 8 使用 `shipping_dept` 作为数据范围代码，以便船员继续落在现有船务人员、提醒和船务工作流的数据范围内；其业务角色仍为权限更窄的 `crew`，不会因此获得 `shipping` 管理角色。

所有通过认证的企业成员始终拥有 `all_authenticated`。成员属于多个部门时，合并所有匹配到的业务角色和部门代码并去重。

多部门成员保留企业微信返回的部门顺序。只要存在 ID 3 至 8 或其他具体部门，ID 1“公司成员”和 ID 2“待设置部门”就不参与主要部门名称展示；如果成员只属于 ID 1 或 ID 2，则仍显示对应名称，避免页面出现空部门。

未知部门 ID 不授予任何额外业务角色或数据范围代码，但保留企业微信返回的部门名称用于展示和诊断。

## 系统管理员权限

`system_admin` 不从任何部门 ID、部门名称或职务推导。继续由 `WECOM_SYSTEM_ADMIN_USER_IDS` 中配置的企业微信 UserID 独立判定。

因此系统管理员位于部门 1、部门 2 或任意业务部门时都能获得 `system_admin`；普通成员即使位于部门 1 或部门 2，也不会获得管理员权限。

## 后端设计

### 数据模型

为 `wecom_users` 增加非空 JSONB 字段 `department_ids`，默认值为 `[]`，并在实体中映射为 `number[]`。新增可回滚的 TypeORM migration。

现有字段继续保留：

- `department_names`：页面展示和人工排障。
- `department_codes`：现有业务数据范围判断。
- `raw_profile`：保留企业微信原始成员详情。

### 登录数据流

1. OAuth2 code 换取 UserID。
2. 获取企业微信成员详情。
3. 规范化并去重 `detail.department` 中的数值 ID。
4. 通过企业微信部门列表解析展示名称。
5. 按固定 ID 映射生成部门代码和业务角色。
6. 独立检查 UserID 是否在系统管理员白名单。
7. 将部门 ID、名称、代码、头像及原始资料一并 upsert。
8. 返回 JWT 和包含部门 ID 的完整用户资料。

部门列表缺少某个已知 ID 时，使用本设计中的标准部门名称作为展示回退；未知 ID 使用可诊断的 `部门 <ID>` 文本，不影响登录。

### 角色重算

`exchangeCode`、`refreshToken` 和 `getCurrentUser` 使用同一角色解析入口：

- 业务角色由已保存的 `departmentIds` 解析。
- `system_admin` 由已保存的独立管理员标记解析。
- 原有“职务包含船员或船长即可获得 `crew`”逻辑保留为兼容回退，部门 8 则始终直接获得 `crew`。

使用统一入口避免登录响应、刷新响应和 `/auth/me` 的角色不一致。

认证用户响应新增向后兼容的 `departmentIds: number[]` 字段，并继续保留现有 `department: string[]` 名称数组。两个数组按同一部门顺序生成，前端可据此准确区分组织根部门、待设置部门和具体业务部门，不依赖中文名称猜测。

## 前端设计

新增轻量的共享用户头像组件，输入用户姓名、头像地址、尺寸和样式类：

- 有头像地址时渲染图片，并设置可访问的替代文本。
- 地址为空或图片加载失败时显示姓名首字。
- 不单独缓存或代理企业微信头像，继续沿用现有 `avatar` 字段。

新增共享部门名称格式化逻辑：

- 按企业微信返回顺序展示全部具体所属部门，而不是只取第一项。
- 去除重复部门。
- 存在具体部门时隐藏 ID 1 和 ID 2；仅有组织根部门或待设置部门时正常显示。
- 使用 ` / ` 分隔多个部门，并允许首页标题在窄屏自然换行。
- 没有可用部门名称时，才根据业务角色提供单个可读回退。

统一替换以下位置：

- “我的”首页用户状态卡片。
- 桌面端页面右上角用户卡片。
- 移动端顶部“更多”按钮中的用户标识。
- 移动抽屉中的用户资料卡片。

## 错误处理与兼容性

- 企业微信没有返回头像时，前端正常回退到姓名首字。
- 头像 URL 加载失败时，不显示破图。
- 空部门数组仍允许登录，只授予 `all_authenticated` 和可能存在的 `system_admin`。
- 旧数据库记录通过 migration 得到空 `department_ids`；用户下一次 OAuth2 登录会补齐真实 ID。
- 在旧用户尚未重新登录前，角色解析可从已保存部门名称兼容恢复既有业务角色，避免部署后立即丢失权限；一旦已有部门 ID，则以 ID 结果为准。

## 测试与验收

### 后端

- 单元测试覆盖部门 ID 1 至 8 的角色和代码映射。
- 验证部门 1、2 不产生额外业务角色。
- 验证部门 8 获得 `crew`、`shipping_dept`，但不获得 `shipping`。
- 验证多部门映射合并和去重。
- 验证系统管理员处于部门 1 或 2 时仍获得 `system_admin`。
- 认证集成测试验证部门 ID、名称、角色和头像被持久化并由 `/auth/me` 返回。
- 验证多部门成员同时获得对应角色，且认证响应中的部门 ID 与名称顺序一致。

### 前端

- 首页使用企业微信头像。
- 桌面右上角、移动顶部和移动抽屉使用同一头像。
- 没有头像时回退到姓名首字。
- 多部门名称完整、去重显示，并在存在具体部门时隐藏 ID 1、2。

### 验证命令

- 运行认证相关后端单元测试和集成测试。
- 运行首页、应用壳层相关前端测试。
- 运行后端和前端类型检查或构建，确认契约无回归。

## 不在本次范围

- 不新增系统内角色管理后台。
- 不根据企业微信部门自动授予 `system_admin`。
- 不代理、下载或长期缓存企业微信头像文件。
- 不恢复或扩展已暂停的 M9 安全业务范围。
