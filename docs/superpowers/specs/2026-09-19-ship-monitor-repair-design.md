# 船舶监控新增与管理链路修复设计

## 背景

船舶监控页面当前要求管理员手工填写 `vesselId`。后端新增 DTO 严格要求 UUID，使用者输入船名或编码时会被全局校验拒绝；页面没有展示提交错误，因此用户看到的是“新增没有反应”。同一链路还存在管理操作不完整、详情权限不足和数据库唯一冲突未转成业务错误的问题。

## 目标与边界

- 继续仅允许 `system_admin` 新增、编辑、启停和删除监控入口。
- 普通登录用户只能读取启用中的监控入口。
- 使用现有主数据船舶选择器，避免页面手填 UUID，也不新增重复的船舶列表接口。
- 修复新增、列表、按船舶查询、详情、编辑、启停和删除的可用性，并覆盖错误反馈。
- 保留首页统计使用的 `vesselId` 字段和现有路由路径；统计文案明确为“监控船舶”，不代表实时在线状态。

## 数据流与接口行为

1. 监控页面调用 `GET /master-data/selectors/vessels` 获取可选船舶，选择器提交真实 UUID。
2. 管理表单提交 `POST /ship-monitors` 或 `PATCH /ship-monitors/:id`；表单错误直接展示 API 返回的 message。
3. API 创建、换船和启用验证船舶未删除且处于 active 状态；原船停用或删除后仍可停用、删除旧入口；同一船舶下重复监控名称返回 409，而不是泄漏数据库异常。
4. 列表和按船舶查询继续只向普通用户返回启用项；系统管理员可用 `activeOnly=false` 查看停用项。
5. 详情接口接收当前用户：普通用户访问停用项按不存在处理，系统管理员可读取管理范围内的停用项。
6. 返回 DTO 动态关联船舶名称和编码（含软删除船舶），保留 `vesselId` 以兼容首页统计。无需增加数据库列或 migration；船舶改名同步显示最新名称，软删除后仍保留可识别的名称。

## 前端组件行为

- 管理表单字段：船舶选择、监控名称、监控地址、访问模式、排序和启用状态（新建默认启用）。
- 新建、编辑、启停和删除都使用统一的 mutation 错误提取逻辑；成功后重置/关闭表单并刷新列表。
- 列表在查询失败时显示可重试的错误状态；空列表显示明确的空状态。
- 管理员列表显示停用项和对应操作；普通用户只看到启用项和“打开”入口。

## 后端实现与安全

- `ShipMonitorService` 的所有读取方法使用当前用户并集中处理可见性。
- 创建/更新保留 `system_admin` 检查，船舶引用检查包含 UUID 校验、软删除和 active 状态。
- 使用服务层预检查并捕获并发唯一约束异常，映射为 `ConflictException`。
- 删除保持软删除语义；已删除记录的更新、删除和详情返回 404。

## 验证

- 前端测试覆盖船舶选择、创建成功/失败、编辑、启停、删除、查询失败和普通用户只读。
- API 单测覆盖 DTO 输入校验；PostgreSQL 集成测试覆盖管理员边界、船舶状态、重复名称和详情可见性。
- 运行前端测试、API 单测、PostgreSQL 集成测试及完整构建，并以本地浏览器验证实际操作。

## 实施确认

- `activeOnly=false` 使用显式字符串转换，修复 Boolean("false") 为 true 的问题；按船舶列表允许管理员查看停用项。
- 页面查询以船舶和权限筛选共同作为缓存参数，使用 currentData 防止切换船舶时显示旧记录。
- HTTP(S) 地址支持 IP、端口及内网域名；必须包含协议，名称去除首尾空格且不能为空。
- embed 模式提供嵌入预览和外部打开入口；第三方平台是否允许嵌入由该平台配置决定。
